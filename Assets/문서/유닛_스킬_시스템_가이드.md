# 유닛 & 스킬 시스템 가이드 (입문용)

이 문서는 "이 코드베이스를 처음 보는 사람"이 유닛/스킬 코드를 읽기 전에 알아야 할 큰 그림만 담는다.
세부 규칙이나 이력은 코드 안 주석에 이미 잘 정리돼 있으니, 여기서는 "어디서 뭘 찾아야 하는지"만 안내한다.

---

## 1. 유닛은 GameObject가 아니다

`Unit`은 Unity의 `ScriptableObject`다. 씬에 떠 있는 캐릭터 GameObject와는 별개의 존재이고,
`UnitGenerate`라는 클래스가 둘을 `Dictionary<Unit, GameObject>`로 연결만 해준다.

```
Unit (ScriptableObject, 데이터+로직)  ←── 별도 관리 ──→  GameObject (화면에 보이는 것)
```

왜 이렇게 만들었는지는 몰라도 되고, "유닛 로직을 고칠 때는 GameObject/MonoBehaviour를 보지 말고
`Unit.cs` / `UnitFunction.cs`를 봐야 한다"는 것만 기억하면 된다.

클래스 구조:
```
Unit (abstract)        — 데이터 + 필드 정의
 └ UnitFunction (abstract) — 실제 동작(이동/피해/시야 등) 구현
      ├ Human   — 인류 (침입자)
      └ Monster — 몬스터 (플레이어가 조종하거나, 야생)
```

**주의**: `Human`/`Monster`는 클래스일 뿐 진영이 아니다. 실제 아군/적 판정은 `unit.FactionBehavior`가
따로 갖고 있고(`HumanFactionBehavior` / `PlayerMonsterBehavior` / `WildMonsterBehavior`), 적인지
확인할 땐 항상 `unit.IsEnemy(other)`를 쓴다.

유닛의 스탯/HP/쿨다운 같은 데이터는 전부 `Unit.Components`라는 리스트 안 여러 "컴포넌트" 객체에
나뉘어 있다(Unity 컴포넌트 아니고 그냥 C# 클래스). 직접 뒤질 필요 없이 `unit.Health.hp`,
`unit.CombatStat.physicalAttack`, `unit.CombatState.State.skillCooldowns` 처럼 이미 만들어진
지름길 프로퍼티로 접근하면 된다.

## 2. 유닛 데이터는 프리팹에 있다 (JSON 아님)

`Assets/Data/units.json`, `skills.json`을 고쳐도 게임에는 **아무 변화가 없다.** 이 둘은 사람이
보기 편하게 만든 원본 데이터일 뿐이고, 실제로 게임이 읽는 곳은 따로 있다.

```
units.json / skills.json  (사람이 편집하는 원본)
        │
        │  상단 메뉴 Tools → GrimArchive → "JSON -> 유닛 프리팹 생성 (원클릭)"
        ▼
Assets/Resources/Units/{유닛이름}.prefab  ← 게임이 실제로 읽는 곳
```

그래서 스탯이나 스킬 수치를 바꾸고 싶으면:
1. json 파일을 고치고
2. 위 Tools 메뉴를 실행해서 프리팹에 반영해야 한다

이걸 깜빡하면 "분명 고쳤는데 왜 안 바뀌지?"가 된다. 실제로 최근에 이 문제로 파이어볼 스킬이
몇 주간 잘못 동작한 적이 있었다.

> ⚠️ **프리팹 인스펙터 우클릭의 "Load Data From JSON"은 쓰지 말 것** (2026-08-23 확인).
> 이쪽은 `JsonUtility`로 `SkillData`를 직접 파싱하는데, `projectilePrefab`/`hitEffectPrefab`은
> `GameObject` 타입이라 JSON에 적힌 이름 문자열("VFX_Fire" 등)을 해석하지 못하고 **null이 된다.**
> 수치와 아키타입은 들어오지만 투사체/이펙트 참조가 조용히 날아가서, 아처의 화살이 노란 사각형
> (폴백 프리팹)으로 바뀌는 식의 퇴행이 생긴다. 위 Tools 메뉴 쪽은 이름→에셋 변환(`FindAssetByName`)을
> 제대로 하므로 안전하다.

## 3. 유닛이 태어나는 법 (스폰)

경로는 여러 개다(인류 웨이브, 야생 스폰, 플레이어 생산 건물 등) — `Assets/Script/Wave/WaveSpawner.cs`,
`GameSession.SpawnWildRoomGuards` 등. 어느 경로든 반드시 아래 3줄이 다 있어야 유닛이 정상 동작한다.

```csharp
var u = unitGenerate.GenerateUnitAtPos<Monster>(unitType, pos, floor); // 생성 + 비주얼 + 스탯 세팅
gameSession.units.Add(u);                  // 매 프레임 처리 대상 목록에 등록
gameSession.RegisterUnitPos(u, u.position); // 충돌/점유 그리드에 등록
```

셋 중 하나라도 빠지면 "보이는데 안 움직인다"거나 "안 보이는데 길을 막는다" 같은 버그가 난다.

## 4. 유닛은 어떻게 "살아있는가" (틱 구조)

MonoBehaviour의 `Update()` 같은 건 없다. 대신 `GameSession`이 매 프레임 모든 유닛을 순회하며
호출해준다. 여기서 헷갈리기 쉬운 건 **두 개의 서로 다른 주기**가 있다는 점이다.

| 주기 | 언제 | 하는 일 |
|---|---|---|
| **`unit.OnUpdate()`** | 매 프레임 (실시간) | HP 재생, 쿨다운 감소, 상태이상 진행, 캐스팅 타이머 등 "시간이 흐르면 그냥 진행되는 것" |
| **`ProcessUnitAction()`** | 유닛마다 다른 주기 (걷는 속도에 따라, 대략 1턴) | "생각하고 행동하는 것" — 아래 FSM이 여기서 돈다 |

즉 체력 재생이나 쿨다운은 매 프레임 부드럽게 흐르지만, "이번엔 뭘 할지 판단하고 한 걸음 움직이거나
공격하는 것"은 유닛별 행동 주기마다 한 번씩만 일어난다. 이 행동 주기 처리를 흔히 "한 턴"이라고
생각하면 이해하기 쉽다.

---

## 5. 유닛의 뇌 — FSM (지금 뭘 하고 있나)

행동 주기마다 유닛은 "지금 어떤 상태인가"를 먼저 정하고(FSM), 그 상태 안에서 "뭘 할지"를 정한다(BT).
상태는 우선순위가 있어서, 위에 있는 조건이 맞으면 아래는 아예 검사하지 않는다.

| 우선순위 | 상태 | 언제 | 하는 일 |
|---|---|---|---|
| 최상위 | **플레이어 명령** | 플레이어가 직접 명령했을 때 | 그 명령(이동/공격)을 끝까지 수행 |
| ↑ | **정지 / 제자리 공격** | 플레이어가 그 명령을 내렸을 때 | 정지=완전 무반응, 제자리 공격=이동 없이 사거리 내 공격만 |
| 높음 | **전투** | 눈에 보이는 적이 있을 때 | 스킬로 싸움 (아래 6장) |
| 중간 | **전술** | 함정/경계/조사 등 특수 상황 | 상황별 대응 |
| 낮음 | **대기** | 딱히 할 일 없는 몬스터 | 제자리 근처에서 배회 |
| 최하위 | **탐색** | 항상 켜져있는 기본값 | 계단 찾기, 정처 없이 돌아다니기 |

유닛 머리 위에 뜨는 라벨(예: "전투", "정지")이 바로 이 상태 이름이다 — **디버깅할 때 제일 먼저
확인할 것.** 코드는 `Assets/Script/Unit/AI/States/` 아래 상태별 파일로 나뉘어 있다.

## 6. 스킬 시스템 기본

스킬 하나 = `SkillAction`(로직) + `SkillData`(수치) 한 쌍이다. 이미 만들어진 스킬 종류(아키타입)가
몇 개 있고, 대부분은 코드를 새로 안 짜도 데이터만 조합해서 쓸 수 있다.

```
전방 공격(Generic) · 화살 등 투사체(Projectile) · 광역 폭발(GroundAoE) · 파이어볼(Fireball)
기습(Backstab, 뒤에서 치면 크리) · 치유(Heal) · 보호막(Shield) · 저주(Curse) · 연타(MultiHit) · 파티버프(PartyBuff)
```

`Fireball`은 `GroundAoE`를 상속한 "메테오"형이다 — 시전자에게서 투사체가 날아가는 게 아니라,
**시전 순간 대상 좌표를 굳혀 예고 타일을 띄우고, `baseDelayMs`(1.5초)가 지난 뒤에야** 그 자리에
범위 판정과 피해가 들어간다. 좌표가 먼저 고정되므로 적은 그 사이에 걸어나가 피할 수 있다.

전투 상태(5장)에 들어간 유닛은 매 턴 "쓸 수 있는 스킬 중 가장 우선순위 높은 것"을 골라 쓴다.
그게 사거리 안에 있으면 실행하고, 아니면 다가가거나(필요하면) 거리를 벌린다.

알아두면 좋은 것 두 가지만:
- **스킬 하나의 코드(`SkillAction`)는 같은 종류 유닛 전체가 공유한다.** 그래서 "이번 공격은 쿨다운
  몇 초 남았다" 같은 개인 상태는 스킬 코드 안이 아니라 유닛 쪽(`unit.CombatState.State.skillCooldowns`)에
  저장한다. 이 원칙만 지키면 크게 문제될 게 없다.
- **쿨다운 슬롯은 4개뿐이다**(`skillCooldowns` 배열 크기 4). 데이터에서 슬롯 번호를 잘못 넣으면
  에러 없이 조용히 그 스킬이 영원히 안 나가니, 새 스킬 추가할 때 슬롯 번호(0~3)를 확인할 것.

## 7. 뭔가 추가하고 싶다면 — 어디를 보나

| 하고 싶은 것 | 볼 곳 |
|---|---|
| 새 유닛 종류 추가 | `UnitTypes.cs`에 클래스 추가 → `units.json` 항목 추가 → `Assets/Resources/Units/`에 프리팹 생성 |
| 스킬 수치만 조정 | `skills.json` 수정 → Tools/GrimArchive/JSON -> 유닛 프리팹 생성 재실행 (2장 참고) |
| 새 스킬 종류(아키타입) 추가 | `Assets/Script/Unit/Skills/`에 `SkillAction_XXX.cs` 추가 → `UnitVisualDefinition.BuildSkillActions()`의 switch에 등록 |
| AI 행동/우선순위 조정 | `Assets/Script/Unit/AI/States/` 각 상태 파일, 수치는 `Resources/FSM+BT/AIBehaviorConfig` |
| 피격/데미지 로직 | `UnitFunction.cs`의 `TakePhysicalDamage` 등 |

핵심 파일 5개만 먼저 열어보면 감이 잡힌다:

```
Unit.cs                 — 유닛 데이터의 전부가 여기서 출발
UnitFunction.cs          — 실제 동작(이동/피해/시야) 구현 (제일 크고 제일 중요)
AI/FSM/UnitFSM.cs        — 상태 전환 규칙
Skills/SkillAction.cs    — 스킬 공통 로직(시전, 히트박스, 데미지 적용)
Visual/UnitVisualDefinition.cs — 프리팹 데이터 정의 + 스킬 조립 공장
