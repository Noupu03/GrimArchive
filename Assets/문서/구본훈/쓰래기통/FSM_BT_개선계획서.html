대상 파일: UnitFSM / PlayerCommandFSMState / CombatFSMState / TacticalFSMState / NavigationFSMState  |  2026-07-28

1. 분석 배경 및 범위

플레이어 명령("명령 잘 안먹혀")이 반복 신고되어 FSM 전체를 분석. 발견된 문제는 크게 두 범주 — 플레이어 명령 실패(직접 체감 버그)와 FSM 설계 결함(잠재적 오작동·유지보수 부채) — 로 나뉜다. 코딩 없이 계획만 수립하는 문서이므로, 각 항목에 구현 범위와 주의사항을 명시한다.

2. 플레이어 명령 실패 케이스
심각 · 즉시 케이스 A — isCastingAttack 블록: 상태는 맞는데 실행이 안 됨

UnitFSM.RunCurrentState()

공격 모션(isCastingAttack = true) 중에 플레이어가 명령을 내리면, SelectState는 올바르게 PlayerCommandFSMState로 전환하지만 RunCurrentState가 return으로 BT 실행을 통째로 건너뛴다. 유닛이 명령을 받았는데 공격 모션이 끝날 때까지 반응이 없어 보임. 공격 속도가 느린 유닛일수록 체감 지연이 크다.

개선 방안
  • 단기: isCastingAttack 체크를 PlayerCommand 상태에서는 예외 처리 — 이동 명령은 공격 모션 중에도 다음 이동 방향만 세팅하고, 모션 완료 후 즉시 실행되도록 큐잉.
  • 주의: 공격 취소를 허용할 경우 공격 판정 타이밍과의 충돌 가능 — 기획 측에 "명령으로 공격 모션 취소 가능 여부" 확인 필요.
  • 대안: isCastingAttack 조건을 유지하되, 명령 수신 시 시각적 피드백(마커 깜빡임 등)을 추가해 "모션 끝나면 실행됨"을 플레이어에게 알림.
심각 · 즉시 케이스 B — ExecutePlayerMove 명령 포기: 명령 내렸는데 유닛이 멈춤

PlayerCommandFSMState.ExecutePlayerMove()

목표 지점이 구조적으로 완전히 막힌 경우 playerMoveTarget = null로 명령을 포기한다. 플레이어 입장에서는 클릭했는데 아무 반응이 없는 것처럼 보임. 현재 포기 시 LogHelper.Warning을 남기도록 임시 처리됐으나, 플레이어에게는 아무 피드백이 없다.

개선 방안
  • 필수: 포기 시 UI 피드백 추가 — FloatingText "이동 불가" 또는 목표 지점 마커를 적색으로 깜빡이게 처리.
  • 선택: 포기 전에 목표 주변 반경을 단계적으로 넓혀가며 도달 가능한 대체 지점을 재탐색(현재는 반경 1칸만 시도). 기존 FindNearbyOpenTile의 탐색 반경 파라미터화.
  • 주의: 탐색 반경을 너무 넓히면 플레이어가 의도하지 않은 지점으로 이동할 수 있음 — 최대 반경 제한값을 Config에서 조정 가능하도록.
심각 · 즉시 케이스 C — HasAnyStructurallyOpenNeighbor 무한 Running: 멈춰서 아무것도 안 함

PlayerCommandFSMState.ExecutePlayerMove() — 2026-07-28 신규 추가 코드

목표 주변에 구조적 빈 칸이 있어 "희망이 있다"고 판단해 명령을 포기하지 않고 Running을 반환한다. 그런데 pathfinding이 실제로는 계속 실패하면(유닛들이 몰려 있거나 경로 자체가 굉장히 우회적인 경우) 유닛이 제자리에 멈춘 채 명령을 처리 중인 척만 하게 된다. 이 코드는 "일시적 혼잡 때 포기 방지" 목적으로 추가됐지만, 혼잡이 풀리지 않는 경우에 대한 탈출 조건이 없다.

개선 방안
  • 필수: Running을 반환하는 횟수에 타임아웃 카운터 추가 — N턴 이상 같은 자리에 있으면 포기 처리(포기 피드백 동일 적용).
  • 구현 위치: ExecutePlayerMove 내부에 stuckCounter 필드(Unit에 추가하거나 PlayerCommandFSMState에 인스턴스 변수로)를 두고, 이동 성공 시 리셋.
  • 주의: 카운터가 너무 짧으면 혼잡 시 포기가 너무 빨리 일어남 — 기획 확인 후 Config에 stuckTimeoutTurns 값으로 노출.
중간 · 단기 케이스 D — SelectState/RunCurrentState 1턴 딜레이: 입력 직후 엉뚱한 행동

UnitFSM.SelectState() / RunCurrentState() — 실행 순서 의존

입력 수신이 RunCurrentState 이후에 처리된다면, 명령이 세팅된 그 턴에는 기존 상태(Combat 등)의 BT가 먼저 실행된다. 다음 턴에야 PlayerCommand로 전환되어 명령이 실제로 실행된다. 이 1턴 사이에 전투 BT가 돌아 다른 적을 공격하거나 엉뚱한 방향으로 이동하는 현상 발생.

개선 방안
  • 확인 선행: UnitFunction에서 입력 세팅 → SelectState → RunCurrentState 순서인지 확인. 이미 올바른 순서라면 이 케이스는 해당 없음.
  • 만약 역순이라면: 입력 처리를 SelectState 이전으로 이동하거나, 입력 수신 직후 SelectState를 한 번 더 명시적으로 호출.
  • 대안: 입력 수신 시 _current?.OnExit() + 즉시 PlayerCommandFSMState로 강제 전환하는 ForcePlayerCommand() 경로 추가 — 단, 현재 상태의 OnExit 부작용을 모두 처리해야 함.
조사 필요 케이스 E — 진단 로그 케이스: 명령이 세팅됐는데 GetPriority가 0을 반환

UnitFSM.SelectState() — 2026-07-28 진단 로그 추가

hasPendingCommand=true인데 PlayerCommandFSMState.GetPriority가 0을 반환해 다른 상태로 전환되는 케이스가 신고됨. HasActivePlayerCommand와 hasPendingCommand는 동일한 필드를 검사하므로 이론상 발생 불가능. 따라서 입력 처리 타이밍 또는 필드를 클리어하는 외부 코드가 원인일 가능성이 높음.

조사 계획
  • 1단계: 실제로 진단 로그가 출력되는지 확인 — 출력된다면 직전 로그의 상태(_current 타입)를 함께 기록하도록 로그 보강.
  • 2단계: playerMoveTarget / isManualMoveCommand 를 변경하는 모든 코드 위치 목록화 — InputManager, UnitFunction, PlayerCommandFSMState 외에 다른 곳이 있는지 확인.
  • 3단계: 원인 파악 후 이 항목을 케이스 A~D 중 해당 케이스로 재분류하거나 별도 항목으로 정의.
3. FSM 설계 결함 (잠재적 오작동 / 유지보수 부채)
설계 결함 · 중요 결함 1 — GetPriority 안의 부수효과 (TacticalFSMState)

TacticalFSMState.GetPriority()

코어 대상 층이 다를 때 hc.pendingStairTargetFloor를 직접 세팅하고 0f를 반환한다. GetPriority는 "조건 평가 → 수치 반환" 만 해야 하는 함수인데 유닛 상태를 변경하는 부수효과가 있다. SelectState가 배열을 순서대로 순회하며 호출하므로, 이 effect가 호출 순서에 묶인다. 나중에 호출 순서가 바뀌거나 GetPriority를 다른 맥락에서 재사용하면 예기치 않은 동작 유발.

개선 방안
  • 원칙: GetPriority는 순수 함수(pure function)로 유지 — 읽기만, 쓰기 금지.
  • 이동 위치: pendingStairTargetFloor 세팅 로직을 OnEnter 또는 BT 내부 CanContinueCore Condition으로 이동.
  • 구체적으로: GetPriority에서는 "층이 다르면 0f 반환"만 하고, 실제 stairTarget 세팅은 TacticalFSMState가 선택됐을 때(OnEnter 또는 CanContinueCore)에 처리.
설계 결함 · 중간 결함 2 — CombatFSMState.OnExit가 항상 alertSearch를 세팅

CombatFSMState.OnExit()

전투 종료 이유와 무관하게 OnExit에서 alertSearch를 항상 세팅한다. "전투 중 플레이어 이동 명령(Combat → PlayerCommand)"에서도 이 코드가 실행돼, 이동 완료 후 적이 없으면 의도치 않게 Tactical(경계) 상태로 진입한다. 플레이어가 목적지에 도착한 유닛이 경계 행동으로 멈춰 있는 것처럼 보임.

개선 방안
  • 전환 이유 구분: 다음 상태(next)가 PlayerCommandFSMState인 경우에는 alertSearch를 세팅하지 않는다.
  • 구현 방법 A: OnExit(Unit unit, IFSMState nextState)로 시그니처 변경해 다음 상태를 파악 — SelectState에서 호출 방식도 수정 필요.
  • 구현 방법 B (더 간단): OnExit에서 setalertSearch하는 대신, "전투 후 경계"가 필요한 상황(Navigation/Tactical 진입 시)에서만 alertSearch를 세팅하는 별도 진입 후처리로 이동.
  • 영향 범위: alertSearch의 생성 위치가 바뀌므로, 경계 발동 케이스 전체 재검증 필요.
설계 결함 · 중간 결함 3 — GetPriority 진입 조건 vs BT 내부 Condition 불일치 (TacticalFSMState)

TacticalFSMState.GetPriority() / HasWait / CanInvestigate 등

GetPriority에서 "Tactical 활성 여부"를 체크하는 조건과, BT 내부 각 브랜치의 Condition이 서로 다르다. 예: GetPriority는 currentWait != null이면 활성화하지만, BT HasWait는 추가로 피격/적 없음까지 확인한다. 결과적으로 Tactical로 진입했는데 모든 BT 브랜치가 Failure를 반환하는 케이스가 존재할 수 있다. 이 경우 상태는 Tactical인데 유닛이 아무 행동도 안 하고 Running만 반환한 채 다음 틱을 기다린다.

개선 방안
  • 원칙: GetPriority 진입 조건과 BT 최상단 Condition은 일치해야 한다 — "GetPriority가 true면 최소 하나의 BT 브랜치가 반드시 Running 이상 반환"을 보장.
  • 단기(방어적): Tactical BT 최하단에 Leaf: DoNothing (→ Running) 폴백 노드 추가 — 모든 브랜치가 실패해도 상태만 유지하고 넘어감. 지금도 사실상 이렇게 동작해야 하지만 명시적으로 보장.
  • 장기(근본): GetPriority의 각 조건과 BT 내부 각 Condition을 같은 헬퍼 함수로 통일. 중복 코드를 줄이고 불일치 가능성 제거.
설계 의도 확인 결함 4 — Panic이 PlayerCommand에 무조건 밀림

UnitFSM._states 배열 순서 / TacticalFSMState.IsPanic()

원본 GOAP에서 Panic은 우선순위 150으로 플레이어 명령보다 높았으나, 현재 FSM에서는 PlayerCommand(200) > Tactical(Panic 포함, 50) 순서로 역전됐다. 정신력이 0%인 유닛도 플레이어 명령이 최우선으로 실행된다. 기획 의도와 맞는지 명확히 해야 한다.

개선 방안 (기획 확인 후 선택)
  • 현행 유지: "플레이어가 공황 상태 유닛도 강제 조종 가능" — 기획 의도가 맞다면 코드 변경 없이 주석만 명확히.
  • 기획 변경 시: Panic 전용 상태를 별도로 분리하고 PlayerCommand보다 높은 우선순위로 배열 맨 앞에 배치. 단, Panic 중에도 명령이 일부 먹혀야 한다면(예: 후퇴 명령만 가능) 별도 PlayerCommandFSMState 내부 Panic 예외 로직 필요.
잠재적 문제 · 낮음 결함 5 — Navigation BFS 탐색 타깃 stale (층 이동 후)

NavigationFSMState.RandomExplore()

currentExplorationTarget이 층을 이동한 후에도 남아있다. 현재 terrain == 0 체크로 부분 방어하지만, 이전 층의 미탐색 타일 좌표가 새 층의 유효하지 않은 위치를 가리킬 수 있다. 맵 크기가 층마다 같다면 실제 문제가 안 될 수도 있지만, 층별 맵 크기가 달라지면 인덱스 오류 가능.

개선 방안
  • 간단한 수정: 층 이동이 완료되는 시점(NavigationFSMState.CrossStairs 완료 후 또는 OnEnter)에 currentExplorationTarget = null을 명시적으로 세팅.
  • 현재 위험도: 층 크기가 모두 같으면 낮음 / 층 크기가 달라질 가능성이 있으면 중간으로 상향.
4. 개선 우선순위 로드맵
단계 항목 이유 예상 영향 범위
① 즉시 케이스 E 조사 (진단 로그 확인) 현재 신고된 버그의 직접 원인 파악 — 결과에 따라 다른 케이스로 재분류 UnitFunction, InputManager

② 단기 케이스 A isCastingAttack 처리 방식 결정 체감 지연 원인 2위 — 기획 확인(취소 허용 여부) 후 구현 UnitFSM.RunCurrentState, 공격 모션 시스템
② 단기 케이스 B 명령 포기 UI 피드백 포기 자체는 허용하되 플레이어에게 알려야 함 — UI 연동 PlayerCommandFSMState, UI FloatingText
② 단기 결함 2 CombatFSMState.OnExit alertSearch 조건화 플레이어 명령 완료 후 의도치 않은 경계 상태로 연결 — 체감 버그 CombatFSMState.OnExit, UnitFSM.SelectState(시그니처 변경 시)
③ 중기 결함 1 GetPriority 부수효과 제거 현재 동작은 되지만 유지보수 위험 — 다음 기능 추가 전에 정리 TacticalFSMState.GetPriority, OnEnter 또는 BT Condition
③ 중기 결함 3 GetPriority vs BT Condition 동기화 잠재적 "아무것도 안 하는" 상태 — 명확한 재현 조건 파악 후 수정 TacticalFSMState 전반, 헬퍼 함수 정리
③ 중기 케이스 D SelectState/RunCurrentState 순서 확인 실제 역순인지 확인 먼저 — 이미 올바른 순서면 skip UnitFunction Update 흐름
④ 장기 결함 4 Panic 우선순위 기획 확인 기획 의도 확인 후 처리 — 당장 버그는 아님 UnitFSM._states 배열, 별도 Panic 상태 가능성
④ 장기 결함 5 BFS 타깃 stale (층 크기 달라질 때) 현재 낮은 위험도 — 층 구조 확장 시 처리 NavigationFSMState.CrossStairs
5. 수정 전 기획/구조 확인이 필요한 사항

아래 항목들은 코드 수정 전에 기획 또는 구조 파악이 선행되어야 한다.

  • 플레이어 명령으로 공격 모션 취소 가능 여부 — 케이스 A의 처리 방식이 달라짐
  • Panic 상태에서 플레이어 명령 허용 여부 — 결함 4 처리 방향
  • UnitFunction의 입력 처리 → SelectState → RunCurrentState 실행 순서 — 케이스 D, E 원인 파악에 필수
  • playerMoveTarget / isManualMoveCommand를 변경하는 코드 위치 전체 목록 — 케이스 E 조사
  • 층별 맵 크기 동일 여부 (현재 및 미래 계획) — 결함 5 우선순위 결정
