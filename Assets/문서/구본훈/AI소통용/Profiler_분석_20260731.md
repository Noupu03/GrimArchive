# 프로파일러 분석 및 최적화 권장안 (2026-07-31)

첨부 3장(`2026-07-31_110210.png`, `110245.png`, `110302.png`)은 Unity 프로파일러 Hierarchy 뷰(Deep
Profile, 에디터 재생 중 캡처)를 이어붙인 것으로 보입니다. `PlayerLoop` 총 88.2%(109.23ms), `EditorLoop`
11.5%(14.30ms self)로, 이 캡처는 **한 프레임이 100ms를 넘는 심한 저프레임 구간**을 잡은 것으로 판단됩니다
(에디터 오버헤드가 섞여 있어 절대 수치는 빌드보다 부풀려져 있지만, 상대적 병목 위치는 그대로 유효합니다).

## 2. 1순위 — 2D 그림자 연산 (가장 큰 병목)

### 수치 근거
- `InlDraw 2D Shadow Texture` 30.5%(37.80ms), `DrawShadow2DPass.ExecuteShadowPass()` 30.9%(38.35ms)
- `ShadowCaster2D.IsLit()` self 3.6%(4.49ms), **9,103회 호출**
- `ShadowCaster2D.CacheValues()` self 1.8%(2.23ms), **25,065회 호출**
- `ShadowCaster2D.get_boundingSphere()` self 1.3%(1.70ms), 36,538회
- `ShadowMesh2D.get_boundingSphere()` self 1.3%(1.65ms), 36,412회
- `ShadowCasterGroup2DManager.FindTopMostCompositeShadowCaster()` 4.1%(5.24ms), 8,855회
- `ShadowRendering.ShadowCasterIsVisible()` 8.6%(10.67ms), 2,654회

이 호출 횟수들은 전형적으로 **"라이트 개수 × 섀도우 캐스터 개수"** 조합만큼 매 프레임 재계산되는
URP 2D 렌더러의 내부 구조에서 나옵니다. 캐스터 수 자체는 코드상 방(room)의 폐곡선 개수만큼만
생성되도록 이미 최적화돼 있는 것을 확인했습니다(`MapRandering.cs:305-308` 주석 — "콜라이더 하나당
경로 하나뿐이라 폐곡선(=대략 방 개수)만큼 오브젝트가 생기지만 타일 개수보다 훨씬 적어 성능 문제는
없다"). 문제는 **라이트 쪽**입니다.

`GameSession.cs:1973-1990` "횃불 배치" 로직을 보면, **시작방을 제외한 모든 방의 모든 청크(8×8
타일)마다 Light2D를 포함한 Torch 프리팹을 하나씩 스폰**합니다. 안개가 걷힌 방만 스폰하도록 지연은
되어 있지만, 한 번 걷힌 방은 이후 화면 밖으로 나가도, 카메라에서 멀어져도 계속 활성 상태로 남습니다.
탐사가 진행될수록 활성 Light2D 개수가 누적되고, 이 라이트들이 (시야에 안 보여도) 매 프레임 맵 전체
캐스터와 컬링/그림자 비교를 반복하는 것이 이번 캡처의 핵심 원인으로 보입니다.

### 권장 조치 (효과가 큰 순서)
1. **화면(카메라 뷰포트) 밖 Torch의 Light2D를 비활성화**하는 컬링 로직 추가. 이미 방 단위로 Room
   경계 정보가 있으므로(`Room.Bounds` 등), 카메라 프러스텀/현재 층 기준으로 안 보이는 방의 Light2D
   컴포넌트만 `enabled = false` 처리하면 캐스터 비교 대상에서 완전히 제외됩니다. (그림자는 끄고 Sprite
   조명 색만 유지하고 싶다면 `light.shadowsEnabled = false`만 꺼도 `ShadowCaster2D.IsLit`/`CacheValues`
   호출 자체가 줄어듭니다.)
2. **Light2D의 `Target Sorting Layers` / Shadow Interaction 범위를 좁히기** — 기본값이면 모든
   레이어의 모든 캐스터와 상호작용을 검토합니다. 횃불 하나가 같은 방/근접 청크의 캐스터만 보게
   범위를 제한할 수 있는지 확인.
3. 위 두 가지가 힘들다면 **동시 활성 Torch 개수에 상한**을 두고(예: 플레이어/카메라로부터 가장 가까운
   N개만 그림자 활성, 나머지는 그림자 없이 은은한 조명만) 절충.
4. 장기적으로는 Unity 2D 라이트 최적화 가이드(URP 2D Renderer의 "Light Overlap"/"Shadow Volume"
   관련 알려진 성능 이슈)를 참고해 라이트 반경 자체를 줄이는 것도 고려.

> 참고: `Renderer2D.InitializeLayerBatches()`(8.45ms), `Light2DCullResult.GetLightStatsByLayer()`
> (8.43ms), `Light2DCullResult.SetupCulling()`(7.21ms) 등 라이트 개수에 비례해 증가하는 항목들도
> 전부 같은 원인(활성 Light2D 개수)으로 묶여 있어, 1번 항목을 해결하면 이 항목들도 같이 줄어들
> 것으로 예상됩니다.

## 3. 2순위 — Unity Object 비교 연산 폭증

- `Object.CompareBaseObjects()` self 2.5%(3.12ms), **39,397회**
- `Object.IsNativeObjectAlive()` self 3.2%(3.97ms), **28,565회**
- `Object.op_Equality()` self 1.6%(2.03ms), 21,019회
- `IntPtr.op_Inequality()` self 2.3%(2.87ms), **64,267회**
- `GCHandle.get_Target()`/`GetRef()`/`get_IsAllocated()` 합산 약 4.3ms, 10,553회씩
- `Object.wbarrier_conc()`(GC 라이트배리어) 1.1%(1.45ms), 27,740회

이 호출들은 전부 `UnityEngine.Object`의 `== null` / 등호 비교가 네이티브 포인터 유효성 확인으로
내려가면서 발생하는 오버헤드입니다. 호출 횟수 규모(수만 회)가 위 섀도우 캐스터 호출 수와 비슷한
자릿수라, **대부분은 URP 2D 렌더러 내부에서 캐스터/라이트 유효성을 프레임마다 재검사**하며 나오는
것으로 추정됩니다 — 즉 1순위 항목을 해결하면 상당 부분 같이 줄어들 가능성이 높습니다.

다만 게임 코드 쪽에도 `Unit`(MonoBehaviour) 참조를 담은 `List<Unit>`에 대해 `.Contains()`를 매 틱
호출하는 곳이 여러 곳 있습니다(`AIState.reactedAttackers.Contains()`,
`InputManager.selectedUnits.Contains()` 등). 이런 자리는 리스트가 커질수록(다수 유닛 난전 시)
`Object.op_Equality` 호출이 선형으로 늘어나므로, 유닛 수가 많아지는 전투 상황에서 별도로 체감될 수
있습니다. 이미 `HashSet` 사용으로 정리된 부분(`ThreatTileRenderer._cachedAliveUnits` 등)도 있으니,
남은 `List<Unit>.Contains()` 호출부 중 프레임당 호출 빈도가 높은 곳(전투 다수 유닛 시나리오)만 골라
`HashSet<Unit>`으로 교체하는 것을 권장합니다.

## 4. 3순위 — 유닛 AI 틱 단가

- `GameSession.ProcessUnitAction()` 17.1%(21.19ms), **호출 8회** → 호출당 평균 ~2.6ms
- `UnitFSM.RunCurrentState()` → `CombatFSMState.Tick()` → `BTLeaf.Tick()` → `ExecuteCombat()` 동일 경로
- `AIMovementHelper.MoveTowardsTarget/Pos()` 9.8%(12.13ms), `AStarMovement.TryGetNextStep()`
  9.7%(12.06ms, 호출 2회), `AStarMovement.IsTileWalkable()` 1,760회
- `UnitFunction.UpdateFOV()` 5.5%(6.83ms), `VisionMath.SymmetricShadowCast()`+`ScanOctant()` 합산
  ~3.7ms

이번 캡처 시점엔 활성 유닛 수가 적어(`ProcessUnitAction` 8회) 절대량은 작지만, **호출당 단가가
2.6ms**로 상당히 높습니다. 전투가 격화되어 동시 행동 유닛 수가 늘어나면 이 구간이 선형으로 증가해
1순위 다음가는 병목이 될 가능성이 큽니다. A* 재탐색(`TryGetNextStep`)이 매 틱 전체 경로를 다시 계산하고
있는지(목적지가 바뀌지 않았는데도 재탐색하는지) 확인해, 필요하면 목적지가 동일할 때 기존 경로를
재사용하도록 캐싱하는 것을 검토해볼 만합니다.

## 5. 다음 단계 제안

   그대로 활용할 수 있어 구현 난이도도 상대적으로 낮음. **최우선 권장.**
2. 위 조치 후 동일한 지점을 다시 프로파일링하여 `Object.CompareBaseObjects`/`IsNativeObjectAlive`
   호출 수가 실제로 같이 줄어드는지 확인 (원인 가설 검증).
3. 그림자 관련 항목이 줄어든 뒤에도 남는 `List<Unit>.Contains()` 호출부를 `HashSet`으로 정리.
4. 유닛 수가 많은 전투 상황을 별도로 캡처해 `ProcessUnitAction`/`TryGetNextStep` 단가가 유닛 수에
   비례해 어떻게 늘어나는지 확인 — 필요 시 A* 경로 캐싱 검토.
