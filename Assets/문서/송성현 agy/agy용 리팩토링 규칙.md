# agy용 리팩토링 규칙

이 문서는 GrimArchive_Prototype 코드베이스에 리팩토링을 제안/수행할 외부 에이전트(agy)에게
전달하기 위해, 이 프로젝트가 지금까지 지켜온 관례와 이번 세션(2026-08-22)에서 실제로 문제가
됐던 사례를 정리한 것이다. 새 규칙을 발명한 게 아니라 **이미 이 코드베이스 전체에 일관되게
적용되고 있던 규칙을 문서화**한 것이다 — 리팩토링이 이 관례들을 깨면 겉보기엔 "더 깔끔한 코드"라도
실제로는 회귀 버그가 된다.

## 0. 가장 중요한 원칙 — 리팩토링은 동작을 보존해야 한다

리팩토링은 "구조를 개선"하는 것이지 "동작을 바꾸는" 것이 아니다. 이 프로젝트는 사용자(기획자 겸
단독 개발자)와의 대화를 통해 수많은 미묘한 규칙이 확정돼 있고, 그 규칙 중 상당수는 **일반적인
코드 리뷰 시각으로는 "왜 이렇게 복잡하게 짜여있지?"로 보이는 것들**이다. 코드를 "정리"하면서
이런 규칙을 조용히 되돌리는 게 가장 흔하고 위험한 리팩토링 사고다.

- 코드에 달린 주석은 대부분 "왜 이렇게 짰는지"에 대한 사용자 요청/버그 이력을 인용하고 있다.
  주석을 지우기 전에 반드시 그 이유가 리팩토링 후에도 여전히 유효한지 확인할 것 — "이 조건문이
  불필요해 보인다"는 판단은 대부분 그 조건문이 왜 생겼는지 아직 이해하지 못했다는 신호다.
- `CLAUDE.md`(프로젝트 루트)에 "하드 룰"로 명시된 항목은 리팩토링 대상이 아니라 절대 불변 조건
  이다. 예시(2026-08-22 기준):
  - 대화 언어는 항상 한국어(코드/커밋/문서/채팅 응답 전부).
  - 자동 오브젝트(코어/문) 공격은 인류 전용 — 플레이어 몬스터는 절대 스스로 코어/문을 공격하지
    않는다. 반드시 플레이어의 명령(우클릭)으로만 시도한다.
  - 문 소유권(`InteractableObject.DoorOwnerFaction`)은 방 점령과 완전히 분리돼 있다 — 방 소유권이
    바뀌어도 문 소유권은 자동으로 안 바뀌고, 파괴 후 재설치로만 바뀐다.
  - 좌클릭은 항상 "선택"만, 우클릭은 항상 "실행"(이동/공격/설치 확정 등)만 담당한다.
  - 이런 항목을 리팩토링 과정에서 우연히라도 건드리게 되면(예: 조건문 통합/단순화 과정에서) 반드시
    먼저 질문하고 진행할 것 — "고쳤더니 사이드이펙트로 하드 룰이 깨졌다"는 사후 통보로 처리하지 않는다.

## 1. 이 프로젝트의 리뷰/검증 환경 제약

이 세션은 Unity 에디터를 직접 실행할 수 없는 환경에서 전부 진행됐다(agy의 환경은 다를 수 있으니
먼저 확인할 것). 그래서 다음 방식으로만 정합성을 검증했고, 이 방식들은 여전히 유효한 최소 안전망
이다 — 에디터 실행이 가능하더라도 생략하지 말 것:

- **브레이스 밸런스 확인**: 파일을 수정할 때마다 `{`/`}` 개수가 일치하는지 확인한다(대규모 리팩토링
  시 특히 중요 — 블록 이동/추출 과정에서 브레이스가 어긋나기 쉽다).
- **그렙 기반 죽은 참조 검증**: 심볼/클래스/메서드를 삭제·이름 변경할 때 반드시 프로젝트 전체를
  검색해서 참조가 남아있지 않은지 확인한다. **`Assets/Script`만 검색하고 끝내지 말 것** —
  `Assets/Editor`(리플렉션으로 private static 메서드를 직접 테스트하는 `FSMVerificationRunner.cs`
  같은 파일이 있다)와 `Assets/Tests`도 반드시 포함해야 한다. 이번 세션에서 실제로 `Assets/Script`
  만 스윕했다가 `Assets/Editor`의 컴파일 에러를 놓친 사고가 있었다.
- **오타/인코딩 이슈 재확인**: 도구에 따라 UTF-8 파일의 `//`가 `\`로 잘못 렌더링되는 등의 표시
  오류가 있을 수 있다(이 환경에서 관찰된 현상 — 실제 파일 내용은 `Read`로 재확인하면 정상이었다).
  이상한 문자가 보이면 지우지 말고 먼저 실제 파일 내용을 다시 읽어 확인할 것.
- **Unity 실행 검증은 별도로 필요**: 코드가 컴파일된다고 해서 의도한 대로 동작한다는 보장은 없다.
  구현현황 문서(아래 2번 참고)에 "검증 상태" 체크리스트를 남겨 실제 플레이 검증이 필요한 항목을
  명시하는 관례를 따를 것.

## 2. 문서 우선 확인 — 구현현황 문서 체계

이 프로젝트는 시스템별로 `Assets/문서/구현현황/구현중/`에 날짜가 박힌 구현현황 `.txt` 문서를
유지한다(예: `새데모_구현현황_2026-08-22.txt`, `가중치_구현현황_2026-07-20.txt`,
`시야인지반응_구현현황_2026-08-05.txt`). 각 문서는 장별 구현 태그(✅완료/🔶부분/❌미구현), 사용자가
확정한 애매한 판단의 근거, "다음 우선순위 구현 후보" 섹션을 담고 있다.

**리팩토링 전 필수 절차**:
1. 건드리려는 시스템에 해당하는 구현현황 문서가 있는지 `CLAUDE.md`에서 먼저 찾아 읽는다 —
   `CLAUDE.md`의 각 시스템 섹션이 어느 문서를 봐야 하는지 안내한다.
2. 그 문서에서 "왜 이렇게 구현했는지"(특히 애매했던 부분을 사용자가 어떻게 확정했는지)를 먼저
   이해한다. 리팩토링으로 구조를 바꾸더라도 그 판단 근거가 되는 **동작 자체**는 유지해야 한다.
3. 리팩토링으로 뭔가 바뀌었다면 그 문서를 직접 갱신한다(장별 태그 업데이트). 대규모 갱신이면 새
   날짜 파일을 만들고 이전 파일은 `구현현황/지난거/`로 옮기는 게 관례다.
4. `CLAUDE.md`에도 해당 시스템 섹션이 있다면 함께 갱신한다 — 특히 "다음에 이 시스템을 확장할 때"
   섹션은 항상 최신 상태를 유지해야 다음 작업자가 다시 조사하지 않아도 된다.

## 3. 코드 스타일 관례

- **주석은 WHY만, WHAT은 쓰지 않는다.** 잘 지어진 이름이 이미 WHAT을 설명하므로, "이 변수는 X다"
  류의 설명은 불필요하다. 주석은 비직관적인 제약, 과거 버그의 원인, 사용자 요청의 정확한 인용
  (따옴표로 그대로 인용하는 관례)을 남길 때만 쓴다.
- **최소 변경 원칙.** 요청받은 리팩토링 범위를 벗어난 "겸사겸사 개선"을 하지 않는다 — 별도
  추상화, 방어적 예외 처리, 미래를 대비한 확장 포인트를 리팩토링 과정에서 임의로 추가하지 않는다.
  기존 컨벤션(예: 순수 함수는 `*Math.cs`에, 부수효과가 있는 호출부는 `*System.cs`에 두는 분리
  패턴)을 그대로 따른다.
- **기존 유사 시스템을 먼저 확인한다.** 이 세션에서 실제로 발생한 실수: "제자리 공격" 상태에
  방향 전환 타이머를 새로 만들었는데, 이미 `UnitFunction.ResolveVisionDirection`(시야 방향 전환
  우선순위 시스템)이 소리/피격 인지 기반 방향 전환을 전부 구현해두고 있어서 오히려 그 시스템과
  충돌해 더 부자연스러워졌다. **비슷한 걸 새로 만들기 전에 반드시 "이미 있는 시스템을 재사용할 수
  있는가"부터 확인한다.**
- **네이밍/파일 구조는 기존 패턴을 그대로 따른다.** 예: `Assets/Script/Unit/Weight/`,
  `Assets/Script/Unit/Vision/`, `Assets/Script/Unit/Propagation/` 같은 기능별 폴더 분리, `*Enums.cs`/
  `*Math.cs`/`*Record.cs`/`*System.cs` 접미사 관례.
- **한국어 사용.** 코드 내 주석, 커밋 메시지, 이 프로젝트에 남기는 모든 문서는 한국어로 작성한다
  (`CLAUDE.md` 최우선 규칙 — 예외 없음).

## 4. 성능 관련 함정 (이번 세션 실제 사고 사례)

"더 정확하게 만들려고" 게이팅 조건을 제거했다가 심각한 프레임 드랍을 유발한 사례가 있었다:
선택 시각화(발밑 링/시야 범위 표시)가 "유닛 상태가 실제로 바뀔 때만" 갱신되던 걸 "매 프레임 무조건
갱신"으로 바꿨더니, (1) 아직 생성 안 된 GameObject들이 한 프레임에 몰려서 생성되며 스파이크가 나고,
(2) 삼각함수 기반 LineRenderer 재계산(콘 그리기)이 매 프레임 불필요하게 반복되며 지속적 비용이
늘었다. 교훈:
- **"항상 최신 상태를 반영해야 하는 것"과 "매 프레임 무조건 다시 계산해야 하는 것"은 다르다.**
  가벼운 상태 토글(`SetActive`, `bool enabled`)은 매 프레임 갱신해도 되지만, 무거운 재계산(메시/
  라인렌더러 지오메트리 생성, 트리거 계산 등)은 "실제로 바뀐 값이 있을 때만" 다시 계산하도록
  더티 체크(dirty-check) 캐시를 둬야 한다.
- **일괄 처리(batch) 도입 시 "몰림" 위험을 항상 검토한다.** 이전엔 여러 프레임에 자연히 흩어져
  실행되던 초기화/생성 작업을, "모든 유닛을 매 프레임 순회"하는 구조로 바꾸면 스폰 직후처럼
  다수 유닛이 동시에 같은 조건에 걸리는 순간 비용이 한 프레임에 몰릴 수 있다 — 가능하면 최초 1회
  비용이 드는 작업(GameObject 생성 등)은 스폰 시점처럼 원래 자연히 분산되는 지점에서 처리한다.
- 이 프로젝트는 유닛 수가 많을 수 있는 웨이브 기반 게임이라 O(유닛 수) 반복 자체는 이미 여러 곳에
  존재하고 용인되는 편이다(예: `GameSession.UpdateProcess`의 매 프레임 유닛 순회) — 문제는 반복
  자체가 아니라 **반복 안에서 하는 일이 무거운데 매번 다시 계산하는 것**이다.

## 5. FSM/BT 아키텍처를 건드릴 때

- 유닛 행동은 `UnitFSM._states` 배열(우선순위 내림차순: PlayerCommand(200) > Combat(100) >
  Tactical(50) > Idle(20) > Navigation(10))과, `PlayerCommandFSMState`/`HaltFSMState`/
  `StandGroundAttackFSMState`처럼 배열 밖에서 `UnitFSM.SelectState`가 직접 강제 배정하는 "고착
  상태" 두 종류로 구성된다. 이 구조 자체(우선순위 배열 + 강제 배정 예외)를 다른 패턴으로 바꾸는
  리팩토링은 사실상 전면 재작성이므로 반드시 먼저 논의한다.
- `TacticalFSMState` 내부는 `TacticalBehaviorPriorityConfig`(ScriptableObject, 없으면 코드
  내 하드코딩된 폴백 순서 사용)로 BT Selector의 자식 순서를 정한다. 새 행동을 추가/제거할 때 이
  두 곳(에셋이 있으면 에셋도, 없으면 폴백 리스트도) 다 갱신해야 한다 — 이번 세션에서 실제로 에셋이
  존재하지 않아 폴백 리스트만 있었다(확인 없이 에셋이 있다고 가정하면 안 됨).
- 채널링/데미지 적용처럼 "여러 진입 경로(자동 AI + 플레이어 명령)가 공유하는 로직"은
  `UnitFunction.OnUpdate`처럼 한 곳에 모아두는 패턴을 따른다 — 경로마다 로직을 복제하면 한쪽만
  고치고 다른 쪽을 빠뜨리는 사고가 나기 쉽다(이번 세션에서 스프라이트 방향 갱신 호출을 한쪽
  경로에서만 빠뜨렸던 사례 있음).

## 6. Git / 실행 관련 주의사항

- 파괴적 git 명령(`reset --hard`, `push --force`, `clean -f`, `checkout --` 등)은 사용자가 명시적
  으로 요청하지 않는 한 사용하지 않는다. 되돌릴 게 있으면 해당 파일만 정밀하게 수동으로 되돌리는
  걸 우선한다(전체 diff를 보고 그 turn에서 실제로 바뀐 부분만 골라 되돌린다) — 이 세션의 나머지
  수십 개 파일에 걸친 미커밋 작업을 함께 날리지 않도록 주의.
- 커밋은 사용자가 명시적으로 요청할 때만 생성한다.
- 리팩토링 규모가 크다면(여러 시스템에 걸침) 먼저 계획을 세워 사용자 승인을 받고 진행하는 걸
  권장한다 — 이 프로젝트는 기획 문서 기반 개발이라, 구조 변경이 기획 의도와 충돌하지 않는지
  확인하는 절차가 특히 중요하다.

## 7. 애매하면 질문한다

`CLAUDE.md`에 명시된 작업 방식 원칙을 그대로 따른다 — 다음 경우는 임의로 판단하지 말고 반드시
먼저 질문할 것:
- 수치/기준이 코드나 문서에 명시돼 있지 않아 새로 판단 근거를 만들어야 하는 경우.
- 기존 코드의 확립된 동작 방식을 리팩토링이 바꿔야 하는 경우.
- 리팩토링 범위가 "최소 정리"와 "구조 전면 개편" 등으로 크게 갈릴 수 있는 경우.
- 위 0번 항목의 "하드 룰"에 조금이라도 영향을 줄 수 있는 경우.
