   ({유형})" 줄을 추가한다.
   **[정정, 2026-09-25 회의록]** 처음엔 "점령/보스공략은 현재 웨이브 구조에서 다른 종류와 구별되지
   않는다"는 판단으로 3종(탐색/회수/소탕)만 구현했었다 — 이는 틀린 판단이었다. 사용자가 회의록

   명시적 설계 의도이고, 점령 파티는 "방어 건물을 세우고 그 방에 머무르며 점령 판정"이라는, 다른
   파티들과 뚜렷이 구별되는 행동을 한다. 아래 결정 5번(코어·점령 재설계)에서 점령 파티 전용
   상호작용을 구현해 되돌렸다. 보스공략은 여전히 별도 파티 종류로 구별할 근거가 문서에 없어 제외

5. **코어·점령 재설계(회의록 09.25 반영, 사용자 최종 확정 지시) — 최종적으로 코어는 보스방 전용화,
   점령 오브젝트는 시도 후 삭제.** 새데모 코어 전면 개편(2026-08-22, "모든 방이 항상 코어 보유")을
   이 회의록이 뒤집었다 — 최형준(팀원): "코어 보스방 하나만 둬", "애초에 점령 파티 외에는 점령 안
   할 거니까 바뀌어야 하는 게 맞음, 점령이 일반 파티는 없음".
   **최종 확정 상태(코드가 지금 이렇게 돼 있다)**:
   - **코어는 보스방에만.** `GameSession.SpawnBossCores`(옛 SpawnAllRoomCores 대체, `FindBossRoom`
     재사용)가 각 층 보스방에만 코어를 배치한다. `Room.CoreObjectId`가 null이면 보스방이 아니라는 뜻.
   - **"임시 점령 오브젝트"는 시도 끝에 완전히 삭제됐다.** 순서: (1) 진행도 기반 상호작용(0~1
     누적, 완료 시 IsOccupyCompleted) → (2) 사용자 재요청("거의 코어와 유사하게: 벽판정/코어처럼
     파괴/명령으로 파괴 가능/방단위 연출/단 인류는 점령 파티만")으로 InteractableObject.OccupyHp
     + MarkTileObstacle + 코어와 동일한 HP 채널링 파괴 메커니즘으로 전면 재작성 → (3) 그 상태에서
     사용자가 "이제 임시 점령 오브젝트는 관련 코드 포함 전부 지워줘. 대신 추후에 다른 점령 조건을
     추가할 수 있으니 세팅만 해주고"라고 최종 지시 → **관련 코드 전부 삭제**(InteractableObject.
     OccupyHp/OccupyMaxHp, GameSession의 OccupyTag/RoomOccupyMaxHp/OccupyAttackDamagePerSecond/
     OccupyRegenDelaySeconds/OccupyRegenPerSecond 상수 + SpawnRoomOccupyObject/TickOccupyRegen,
     Room.OccupyObjectId/OccupyPosition, TacticalBehaviorType.Occupy 전체(BT 노드/우선순위 설정
     항목/HasOccupyTarget 계열 5개 메서드), UnitFunction.OnUpdate의 isOccupy 채널링 분기,
     PlayerCommandFSMState/BuildingControlPanel의 Occupy 분기 — grep으로 전수 확인, 잔재 없음).
   - **"세팅"으로 의도적으로 남겨둔 것**: `PartyType.Occupy`(4번째 파티 종류)와
     `Party.IsRoomActivityComplete`의 `case PartyType.Occupy: return room.RoomFaction ==
     FactionType.Human;`(트리거 조건과 무관하게, "방이 인류 소유가 되면 완료"라는 판정 기준 자체는
     유지). 다음 점령 조건을 만들 때 참고할 패턴: `OffenseProcessor.OnCoreDestroyed`가 "체력 0 →
     ApplyRoomOwnership + 방어적 재확인(이미 같은 진영이면 조용히 처리)" 구조의 예시. `IMapColorizer.
     PulseRoomOutline`(방 테두리를 진행파로 웅웅거리게 하는 연출, 아래 참고)은 이미 완성돼 있고
     점령 조건과 무관하게 재사용 가능 — 다음 트리거가 뭐든 방 소유권이 바뀌는 순간 이걸 호출하면 됨.
   - **점령 연출(방 테두리 펄스)은 삭제되지 않고 남았다** — 임시 오브젝트와는 독립적인, "방 소유권
     변경 시 재생할 공용 연출" 인프라라 사용자가 명시적으로 "마음에 드네"라고 승인한 뒤 삭제
     대상에서 제외했다. `IMapColorizer.PulseRoomOutline` + `MapRandering` 구현 — 방 테두리
     LineRenderer(들)의 굵기/밝기를 waveCount=3개 봉우리가 travelSpeed=초당1.5바퀴로 도는 감쇠
     사인파로 1.5초간 흔든다(위치별 위상 차이로 "퍼지는" 느낌, 사용자 2차 피드백 반영). 현재는
     호출부가 없다(OnRoomOccupied가 삭제됐으므로) — 다음 점령 조건의 트리거 지점에서 호출하면 됨.
   - **의도적으로 범위 밖에 둔 것(회의록이 스스로 미확정이라고 밝힌 부분 — 임의 판단 아님)**:
     (a) 층 통제권 상실 — 최형준: "통제권 역할 뭐로 할지 명확히는 미설정"; (b) 인류 유닛의 거점
     잔류 — 최형준: "이는 고민 좀 더"; (c) 점령 파티의 "방어 건물 설치"(목책 등) — 건설 시스템
     확장 필요; (d) 방 클리어(적대 유닛 전멸 시 건설/배치모드 권한 부여) — 점령과는 별개 개념,
     기존 OffenseProcessor._activeOffenseRooms(플레이어 몬스터의 야생 침공 추적, 다른 목적)와
     혼동하지 말 것. 최형준이 시사한 "진짜" 점령 방식(오브젝트가 아니라 점령 파티가 방어 건물을
     실제로 건설하는 연출)도 여전히 미착수 — 건설 시스템이 생기면 그쪽으로 갈 가능성이 높다.

   새데모 개편(코어 전면 개편 — "모든 방이 코어를 항상 보유, HP 파괴=즉시 점령")때 삭제된

   이름이 겹치지만, 새 03번 문서 자체가 "코어 조사 완료는 코어 파괴나 층 개방 완료와 별개의 사건"
   이라고 명시한다 — 즉 "조사"가 "어떻게 점령하는가"를 대체하지 않는다. 그래서 이번 구현에서
   "코어 발견→리더 조사"는 **파괴 매커니즘(HP/CoreAttack 채널링)을 되돌리지 않고, "코어를 발견하면
   그 정보를 리더에게 보고하고 파티 우선순위를 그 코어로 모으는" 리포트·집결 트리거로만** 재구현한다
   (리더가 도착하면 "확인됨" 처리하고 코어 우선순위 잠금을 걸어 파티원들이 몰려들게 하는 정도 —
   실제 파괴는 그 뒤로도 계속 CoreAttack/플레이어 명령 채널링이 담당). 8초 조사 타이머 같은 구식
   디테일은 가져오지 않는다.

     음유시인(전투의 노래)→원거리지원.
   몬스터/야생(근접 탱커·인형기사·놀·고블린후드·야생몬스터A·보스골렘·기사형)은 전부 육중한 내리찍기류

  4. 코어 발견 보고·상호작용

    다만 트리거를 "전투 후 스윕 종료"뿐 아니라 "파티종류별 방 활동 완료"(Party.
    TickRoomActivityCheck, 리더 한정 1초 주기)로 확장.
  - "다음 방 이동"(8단계표 5번 후반) = 새 WaitReason.AdvancingToNextRoom + WaitState 재사용.
    HumanWaveManager가 목적지(다음 문)만 지정하고 실제 이동/중단/재개는 TacticalFSMState.ExecuteWait이
    담당 — Wait은 Tactical(50) 안에 있어 Combat(100)에 자연히 밀린다(아래 "중요 발견" 참고).
  - "코어 발견 보고"(8단계표 4번)·"파티 임무"(8단계표 6번, 01번 개인 비전투 목표)는 아직 미착수 —
    기존 Investigate/Navigation 조합이 최소한의 대체 역할을 한다(오브젝트 조사 + 타일 프론티어 탐색).
  - CoreAttack/DoorAttack(기존, 인류 전용)은 변경 없음 — 방 활동 완료 판정이 코어 파괴 자체를 요구하지
    않으므로, 아직 안 뚫린 적대 문에 막히면 개인이 자연히 이 기존 전술로 빠진다(막힘→Wait 해제→
    CoreAttack/DoorAttack으로 자동 위임, 별도 연결 코드 불필요 — TacticalBehaviorPriorityConfig 순서가
    이미 그렇게 짜여 있었다).

**중요 발견(2026-09-25, 구현 중 확인)**: `HumanWaveManager`가 기존에 쓰던 "playerMoveTarget=대상 +
isManualMoveCommand=false" 패턴은 실제로 어떤 이동도 발생시키지 않는 것으로 보인다 —
PlayerCommandFSMState/UnitFSM 양쪽 다 이동 판정에 `playerMoveTarget.HasValue && isManualMoveCommand`
(AND)를 요구하는데 HumanWaveManager는 항상 뒤엣것을 false로 남겨뒀다. 코드 전체를 grep해도 이
조합을 소비하는 경로가 없다(UnitGenerate.cs/InputManager.cs의 사용처는 전부 UI 표시·인구수 계산용).
즉 예전 "코어로 강제 직행"도, 지금 남아있는 퇴각(_retreating) 분기의 "탈출지점으로 강제 이동"도
FSM상으로는 무효한 대입이었을 가능성이 높다 — 실제로 웨이브가 진행되고 퇴각이 완료되는 것처럼
보였다면 자유탐색(NavigationFSMState)과 자동 CoreAttack(인지만으로 발동, 이동 명령 불필요)만으로
설명 가능하다. **이번 신규 기능(집결 후 다음 방 이동)은 이 함정을 피해 WaitState 기반으로 새로
구현**했으므로 실제로 작동한다. 다만 **퇴각(_retreating) 분기는 기존 동작 그대로(수정 안 함, 범위
밖) 남겨뒀다** — 똑같이 무효할 가능성이 있다. 사용자 확인 후 원하면 같은 WaitState 패턴으로
고칠 수 있다(사용자 피드백 메모리 규칙 — 발견한 버그는 확인 후 수정).

    아무 점령 오브젝트도 없는지, (b) 점령 파티(PartyType.Occupy)로 배정된 인류가 실제로 이상하게
    행동하지 않는지(현재는 트리거가 없어 그냥 다른 파티처럼 행동해야 정상), (c) 02번 전투 시스템
    (SelectAttackTarget/보스집중/일반치료/긴급보호)과 01/05번 집결·다음방이동 흐름을 웨이브 하나
    끝까지 실제로 돌려서 확인 — 이 부분은 지금까지 전혀 실제 플레이 검증이 없었다.
13. [다음 세션에 점령을 다시 다룰 때 시작점] 실제 점령 조건을 정할 때 검토할 후보 두 가지:
    (a) 회의록에서 최형준이 시사한 "점령 파티가 방어 건물을 실제로 건설하는 연출" — 건설 시스템
    확장 필요. (b) 그 외 사용자가 새로 지정하는 조건. 어느 쪽이든 트리거 지점에서
    OffenseProcessor.OnCoreDestroyed 구조를 본떠 방 소유권 전환 메서드를 만들고, 그 안에서
    IMapColorizer.PulseRoomOutline을 호출하면 연출까지 바로 연결된다(이미 완성돼 있음).
