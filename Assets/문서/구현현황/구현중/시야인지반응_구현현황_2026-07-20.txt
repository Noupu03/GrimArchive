■ 추가 수정(2026-07-20, 같은 날 성능 이슈 리포트로 발견) — perceptionRecords 무한 성장 + IsAlert O(n)
════════════════════════════════════════════════════════════════════════
02문서 구현 직후 "프레임이 5까지 떨어진다"는 리포트를 받고 확인한 결과, 이번에 새로 만든
Unit.perceptionRecords가 원인이었다. 두 가지가 겹쳐서 문제가 됐다:
1. perceptionRecords는 "이 관찰자가 본 적 있는 대상"을 유닛이 죽거나 오브젝트가 사라져도 지우지
   않는 구조였다 — 웨이브가 반복될수록 죽은 몬스터에 대한 destroyed 참조가 관찰자마다 계속 쌓였다.
2. Unit.IsAlert가 이 딕셔너리 전체를 매번 순회(O(n))했는데, 이 프로퍼티를 읽는
   UnitFunction.ForceRollPerception이 "피격마다 무조건 재판정"하는 IsAttackerIdentified(17장 게이팅)
   경로에서 매 타격마다 호출된다 — 즉 웨이브를 거듭할수록 커지는 n에 대해 전투 중 타격마다 O(n)
   스캔이 반복되는 구조였다. 세션 초반엔 안 느껴지다가 웨이브가 여러 번 돌고 나면 급격히 무거워지는
   패턴과 "갑자기 5프레임" 증상이 정확히 들어맞는다.
수정:
- Unit.IsAlert를 O(n) 순회 대신 _alertRecordCount(카운터) 기반 O(1) 프로퍼티로 교체.
  PendingSuspiciousInvestigation이 바뀌는 유일한 지점(UnitFunction.ForceRollPerception)에서
  Unit.NotifyPerceptionSuspiciousChanged(old,new)로 카운터를 갱신.
- GameSession.RemoveDeadUnit/DespawnUnit에 ClearPerceptionRecordsFor(dead) 추가 — 유닛이 죽는
  시점(사망은 매 프레임 일어나지 않으므로 O(units) 비용을 여기서 감당)에 전 유닛의
  perceptionRecords에서 그 유닛에 대한 기록을 Unit.RemovePerceptionRecord()로 제거한다.
참고(이번엔 안 건드림, 낮은 우선순위): 오브젝트(전리품/시체/전멸흔적) 회수·파괴 시에도 발견자의
perceptionRecords에 obj.Id 항목이 그대로 남는다 — 다만 이건 "유닛당 한 번 본 대상 전체"가 아니라
"세션 동안 스폰된 오브젝트 총수"에 비례해서 유닛 사망 케이스보다 훨씬 작게 자란다. PersonalMapKnowledge.
OnObjectCollected/OnObjectDestroyed 호출 지점에서 같은 방식으로 정리할 수 있음.

■ 사용자 확인이 필요했던 4가지 판단(2026-07-20, AskUserQuestion으로 직접 확인) — 전부 채택된 답
════════════════════════════════════════════════════════════════════════
1. 인지 지속성 아키텍처 — "전체 구현" 채택. 매 UpdateFOV(=매 턴)마다 personalSpottedEnemies를
   Clear() 후 다시 채우던 기존 "매턴 스냅샷" 구조를 유지하되, 그 밑에 대상별(Unit.perceptionRecords,
   키=적 유닛 Unit 참조 또는 InteractableObject.Id) 지속 판정 상태를 새로 깔았다 — 트리거(최초 진입/
   재진입/완전 차단 후 재등장/수상한 타일 2칸 재접근/피격 시 강제 재판정) 시점에만 확률표를 다시
   굴리고, 그 사이엔 PerceptionRecord.Outcome을 그대로 유지한다. 상세 구현은 아래 4장 항목 참고.
2. 경계 상태의 "타일 접근" 이동 — "판정 로직만 구현, 이동은 스텁" 채택. 수상한 타일 상태/임시
   위험도·흥미도(+5/+5)/경계 감지 보정(+20)/2칸 이내 재판정/시야 방향 전환 후보(Alert, 9순위)까지는
   전부 실제로 연결했지만, 유닛이 실제로 그 타일까지 걸어가는 GOAP 목표/이동 행동은 만들지 않았다
   — 04_탐색반응·경계·조사·함정대응 문서가 아직 없어 "어떤 속도로, 어떤 우선순위로 접근하는가"를
   판단할 근거가 없다.
3. 공격자 정체 인지 게이팅 — "게이팅 추가" 채택(17장). Unit.lastAttacker 필드 자체는 기존처럼 피격
   즉시 무조건 세팅되지만(사망 시 시체 causer stage 등 내부 판정에 여전히 필요), 이제 그 값을 근거로
   "공격자가 누구인지 아는 정보 이벤트"(E_HIT_HEAVY_SELF/SEEN, E_STATUS_SELF/SEEN,
   ApplyPerHitDangerDecreaseCheck)를 기록하기 전에 UnitFunction.IsAttackerIdentified()로 인지 판정을
   강제로 한 번 굴린다(4장 조건5 "피격 후 가시성 증가 반영 재판정"의 실제 발생 지점이 바로 여기다).
   인지 실패 시 이 이벤트들은 기록되지 않는다 — hp 차감(TakeDamage)은 이 판정과 무관하게 이미
   확정돼 있으므로 "맞은 사실"까지 사라지지는 않는다. 다만 BroadcastWitnessEvent(제3자 목격 근사)는
   이번 범위에서 손대지 않았다 — 기존에도 "그 순간 생존한 인류 전원이 목격"이라는 근사였고, 목격자
   각자의 인지 판정까지 게이팅하면 관찰자 수만큼 판정을 또 굴려야 해서 범위가 커진다(알려진 한계로
   남겨둠).
4. 정신력 6단계 임계값 — "기존 코드 수치와 무관하게 이 문서만으로 새로 정함" 채택(9장). 기존
   WeightEnums.MentalErrorState(정보 오차용, 25%/50% 2단계)와는 완전히 별개로, PerceptionMath에
   0~100% 균등 6분할(경계값 17/33/50/67/83, 보기 좋은 정수로 반올림)을 새로 만들었다 — ratio가 높을
   수록(정신력이 가득 찰수록) 상위 단계(흥분 +10)로 간다는 문서 본문("정신력이 높으면 유리")만
   근거로 삼았다. maxMental<=0(스탯 미설정)이면 안정(0) 취급 — 그렇지 않으면 항상 ratio=100%가
   되어 미설정 유닛 전원에게 공짜 +10 보정이 붙는 부작용이 생긴다.

02장. 인지·정보판정·실패처리 시스템
════════════════════════════════════════════════════════════════════════
✅ 1장. 개요 — 구현 대상 아님(안내 장).
✅ 2장. 인지 판정 대상 — 유닛(가시성/은신 기반 확률 판정), 시체/전멸흔적(가시성 100 기반),
   일반 타일(안전 확인)까지 실제 구현. 함정/건물은 대응 엔티티가 아직 없어(기존 갭 유지) 여전히
   ❌ — 생기면 InteractableObject 경로를 그대로 타면 된다(BaseVisibility만 쓰는 "그 외" 분기).
✅ 3장. 인지 판정의 기본 결과 — PerceptionOutcome(AccuratePerception/SuspiciousTile/Unrecognized)
   3종 + 안전 확인(기존 TickTileSafety) + 간접 인지(아래 24~25장, 값만 스텁)까지 전부 대응.
✅ 4장. 인지 판정 발생 조건 — "매 프레임 반복 처리가 아니다"를 실제로 구현. Unit.perceptionRecords
   (대상별 지속 상태) + UnitFunction._reachedPerceptionThisPass(패스별 도달 집합) +
   ResolveReachedTarget(트리거 감지)/ForceRollPerception(확률표 롤)으로 최초 진입/재진입/완전 차단
   후 재등장(조건1~3, "지금 안 보이다가 다시 보임"이라는 동일 신호로 통합 처리)/수상한 타일 2칸
   재접근(조건4)/피격 후 재판정(조건5, IsAttackerIdentified가 강제 호출)까지 5개 조건 전부 실제
   트리거 지점을 가진다. "조사·상호작용은 인지 판정 발생 조건이 아니다"/"피격·전투음·전파·공격
   방향 추정 자체는 인지 판정 발생 조건이 아니다"는 애초에 그런 트리거를 만들지 않아 자연히 성립.
✅ 5장. 인지 판정 기본 조건 — Unit.CanPerceive(조건3: 판정 가능 상태)가 ResolveReachedTarget에서
   게이팅. 상태 표는 기절(stunDuration, 유일하게 존재하는 상태이상)만 실제로 막는다 — 수면/마비/
   행동불능은 대응 상태이상 시스템 자체가 없어 🔶(문서가 "차후 상태이상 문서에서 수정/추가될 수
   있다"고 명시한 부분이라 그 문서가 생기면 CanPerceive에 조건만 추가하면 됨).
✅ 6장. 가시성 산출 기준 — 은신 보유 대상(기존 VisionMath.FinalVisibility)/함정·특정 건물(대상
   기본 가시성, 대응 엔티티 없어 🔶)/일반 건물·시체·전멸흔적(가시성 100 고정, VisionMath.
   ResolveObjectVisibility 신규)/일반 타일(안전 확인, 기존)까지 표 그대로. "특정 건물 여부는 건물
   데이터에서 지정" 부분만 건물 엔티티 부재로 미검증.
✅ 7장. 은신 기반 가시성 공식(100-은신, 음수 허용, 클램프는 최종 단계에서만) — 기존 VisionMath.
   FinalVisibility가 이미 이 그대로 구현(01-A 9장과 동일 공식, 변경 없음).
✅ 8장. 최종 가시성 계산 — 대상 가시성(VisionMath.FinalVisibility, 기존)+경계 반영 감지 보정
   (PerceptionMath.DetectionCorrection, 신규)+정신력 보정(PerceptionMath.MentalCorrectionForHuman,
   신규)+공격 후 가시성 증가(기존, FinalVisibility에 이미 포함) 전부 PerceptionMath.
   TotalPerceptionVisibility로 합산. 문서 11장 예시(-50+40+10=0)와 동일한 형태의 예시를 테스트로 고정.
✅ 9장. 정신력 보정 — 6단계 전부 구현(PerceptionMath.MentalTier/MentalVisibilityCorrection). 인류
   전용, 몬스터는 항상 0(Unit.GetMentalVisibilityCorrection의 `this is Human` 분기). 임계값은 위
   "사용자 확인" 섹션 4번 참고 — 문서가 명시하지 않은 값이라 밸런스 조정 여지가 크다.
✅ 10장. 경계 상태 보정(+20) — PerceptionMath.DetectionCorrection + Unit.IsAlert(수상한 타일
   확인 대기 중인 레코드가 하나라도 있으면 true). "시야 거리/인지 거리/인지각에도 반영"은 이번엔
   반영하지 않음 — UpdateFOV의 viewDistance/perceptionDistance/perceptionAngle 계산은 여전히
   spotting 그대로 쓴다(경계 보정을 매 프레임 시야 범위 자체에 반영하면 인지 판정용 감지 보정과는
   다른 새 상태 전파 경로가 필요해 이번 범위를 넘어선다고 판단 — 판단 근거만 남기고 다음 라운드
   후보로 미룸, 🔶).
✅ 11장. 공격 후 가시성 증가 — 01-A 9장과 완전히 동일 항목(기존 구현 재확인, 변경 없음).
✅ 12장. 인지 결과 확률표 — PerceptionMath.OutcomeProbabilities/RollOutcome, 문서 표 그대로 6구간
   고정. roll01은 UnityEngine.Random.value를 호출부(ForceRollPerception)가 넘긴다(함수 자체는 순수
   함수로 유지해 테스트에서 경계값을 고정 검증).
✅ 13장. 일반 타일 안전 확인 — 기존 PersonalMapKnowledge.TickTileSafety(가중치 시스템 15장, 이번에
   손대지 않음)가 이미 근사 구현. "인지 가능한 유닛/오브젝트 없음" 판정이 이제 확률적 미인식까지
   반영하게 됐다(위 01장 5절 항목 참고).
✅ 14장. 정확 인지 — "인지 결과 정보 생성"(RegisterObject/ObserveMonster 등, 기존 경로)과 "반응
   후보 생성"(PerceptionMath.ReactionCandidatesFor + PerceptionReactionCandidate enum, 신규) 둘 다
   실체가 있다. 다만 반응 후보는 VisionDirectionReason과 동일한 전례로 "후보 조회 API"까지만 —
   실제로 하나를 골라 행동으로 옮기는 소비자(04/06/08 문서)가 없어 🔶.
🔶 15장. 정확 인지 후속 처리 — 대상 종류별 반응 후보 5종 표를 PerceptionMath.ReactionCandidatesFor
   (PerceptionTargetKind별 조회)로 그대로 옮겼다. 함정/건물 카테고리는 대응 엔티티가 없어 실질적으로
   호출되지 않는다(EnemyUnit/Corpse/WipeoutTrace만 실제 발생). 소비자 없음 — ❌ 아님(공식/데이터는
   있음)이라 🔶.
✅ 16장. 직접 인지 — 유닛 확인/오브젝트 확인/일반 타일 안전 확인 3가지 다 기존+신규 경로로 구현.
   "조사·상호작용은 직접 인지 조건 아님"은 애초에 그런 트리거가 없어 자연히 성립.
✅ 17장. 직접 피격과 공격자 인지 — 피격 사실/피해량 확정(TakeDamage, 기존)과 공격자 정체 인지
   판정(IsAttackerIdentified, 신규)이 분리됐다. 공격 형태별 방향 정보 표(근접/투사체/원거리/
   투사체마법=방향 확인 가능, 광역/장판=방향 불명, 함정=방향 정보 없음)는 ❌ — TakePhysicalDamage/
   TakeMagicalDamage 시그니처에 "공격 형태" 정보 자체가 없고, 이 정보를 실제로 쓸 소비자(06_전투
   반응·기습 문서의 방향 전환/목표 재설정 후보)도 아직 없어 이번 범위에 넣지 않았다(판단 근거: 위
   "사용자 확인" 섹션 3번).
✅ 18장. 인지 실패 — 수상한 타일/미인식 둘 다 구현(20~22장, 19장 참고). "대상이 존재하지 않는다는
   뜻이 아니다"는 정확히 그대로 성립 — 미인식/수상한 판정이어도 실제 오브젝트/유닛은 그대로 존재.
✅ 19장. 미인식 — PerceptionOutcome.Unrecognized. "안전타일로 처리"는 등록을 건너뛰는 기존 경로
   (RegisterObject/ObserveMonster 미호출)로 자연히 성립.
✅ 20장. 수상한 타일 — PerceptionOutcome.SuspiciousTile + PerceptionRecord.
   PendingSuspiciousInvestigation. 표의 6개 항목 중 "정확한 대상 유형 확인 X"/"공격 대상 지정 X"/
   "전파 X"는 애초에 그런 경로를 안 만들어서 자연히 성립. "경계 상태로 접근 O"는 판정/보정까지는
   구현(Unit.IsAlert), 실제 이동 행동은 스텁(사용자 확인 2번). "시야 방향 전환 후보 O"는
   ResolveVisionDirection()의 Alert(9순위) 후보로 실제 연결(신규).
✅ 21장. 수상한 타일 임시 위험도/흥미도(+5/+5) — PerceptionRecord.TempDanger/TempInterest(계산
   프로퍼티, Outcome==SuspiciousTile일 때만 값을 가짐 — 문서의 "저장값이 아니다"를 그대로 반영해
   PersonalMapKnowledge의 영구 타일 위험도/흥미도에는 기록하지 않는다). 3가지 종료 조건 중 1번(2칸
   이내 재인지에서 정확 인지)과 2번(미인식)은 ResolveReachedTarget이 outcome을 바꾸는 순간
   PendingSuspiciousInvestigation도 함께 false가 돼 자동으로 성립. 3번(수상한 타일 유지 → 직접
   이동 시도 → 점유/함정 작동으로 확인 종료)은 이동 행동 자체가 스텁이라 ❌ — 04 문서가 생기면 이
   흐름의 도착 지점에서 강제로 AccuratePerception 판정을 굴리는 훅을 추가하면 된다.
✅ 22장. 수상한 타일 확인 흐름 — 2칸 이내 접근 시 "일반 인지 판정 + 경계 상태 보정"으로 재판정하는
   구조(ResolveReachedTarget의 suspiciousReapproach 트리거 + IsAlert가 자동으로 감지 보정에 +20을
   더함)까지 구현. "정확 인지/미인식 시 임시값 제거 + 경계 해제"도 Outcome 변경과 동시에 자동 성립.
   "수상한 타일 유지 시 직접 이동 시도" 이하(실제 대상별 처리 표: 유닛/건물 점유로 이동 못 함,
   함정은 도착 시 작동)는 21장과 동일 사유로 ❌.
✅ 23장. 안전 확인과 인지 실패의 관계 — 기존 TickTileSafety 근사 + 미인식 시 안전타일 취급(19장)이
   합쳐져 문서 그대로 성립. "실제로 유닛/함정/건물 등이 존재해도 안전타일로 인지"는 확률적 미인식
   케이스가 실제로 발생하게 되면서 더 이상 이론상으로만 맞는 문장이 아니게 됐다.
🔶 24장. 간접 인지 — PerceptionMath.IndirectCombatPositionTempDanger(10)/
   IndirectNonHostileTempInterest(3) 상수만 존재. 08_전파·소리·간접입력 문서/시스템이 없어 전파/
   전투음/공격 방향 추정/아군 반응 4종 중 어느 것도 실제 발생 지점이 없다(CLAUDE.md가 이미 명시한
   기존 갭 — HumanKnowledgeBase.RecordEvent(..., InfoType.Indirect) 호출부가 여전히 0곳).
🔶 25장. 간접 인지의 임시 위험도/흥미도 — 24장과 동일 사유로 값만 존재, 소비자 없음.
✅ 26장. 인류와 몬스터의 차이 — 표의 8개 항목 중 "정신력 보정"(9장, 인류 전용)/"대표 가중치 정보
   입력"(기존, 인류 전용)은 이번에 재확인. "인지 판정"/"직접 인지"/"전투음·위험 방향 반응"은 양측
   공통으로 이미 구현(CastRay가 Human/Monster 구분 없이 동작). "전파"(인류 전용)는 08 문서 부재로
   양측 다 ❌(24장과 동일 사유). "리더 명령"/"역할군 AI"는 이번 범위 밖(09/기존 GOAP).
✅ 27장. 조정 가능한 파라미터 — 전부 PerceptionMath 상수로 하드코딩 없이 관리(문서가 요구한 대로).
