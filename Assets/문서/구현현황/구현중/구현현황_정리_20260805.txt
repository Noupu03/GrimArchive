■ 1. E_HIT_HEAVY_INDIRECT / E_MONSTER_KILL_INDIRECT 연결
════════════════════════════════════════════════════════════════════════
[배경]
대표 가중치 3종 시스템(이해도/위험도/흥미도) 문서 3-1장에 정의된 간접 파악(InfoType.Indirect) 이벤트
중 두 개가 07 소리 시스템 자체는 이미 구현돼 있었음에도(2026-07-31) 실제 발동 지점이 없었다. 가중치
구현현황 문서 "다음 우선순위 4번", 시야인지반응 구현현황 문서 "다음 우선순위 1번"이 공통으로 가리키던
항목이라 오늘 최우선으로 진행했다.

  소리(피격 발생 공격음/피격 비명)로 접근해서 공격자를 정확 인지하면 기록.
  - UnitFunction.RecordHitWeightEvent가 이 조건을 판정해 소리 발생 시 메타데이터(공격자/heavy 여부/

    시점(추정 지역 접근 후 첫 롤)에서 호출. 공격자를 정확 인지했는지 확인 후 HumanKnowledgeBase.
    RecordEvent 호출.
  - incidentId를 원본 피격 이벤트와 공유해서 SELF/SEEN/INDIRECT가 같은 사건으로 묶이게 함(6장 전역

  - HumanKnowledgeBase.RecordEventByKey 신설 — target: Unit 대신 스냅샷 키(string)를 직접 받는
    경로. 기존 RecordEvent(target: Unit)는 이 메서드를 호출하는 얇은 래퍼로 리팩터링(동작 동일).

■ 2. 소리 시스템 아키텍처 재설계 — 폴링 → 이벤트 기반
════════════════════════════════════════════════════════════════════════
[배경]
위 1번 작업 도중 만든 임시 디버그 시각화(아래 6번)를 사용자가 직접 켜보다가 "소리 유효시간 5초가
원래 이렇게 긴가?"라고 질문 → 07-A 7-3장("일반 소리 유효시간: 발생 후 5초")을 확인시켜줬는데, 이어서
사용자가 그 5초의 실제 의미를 정정했다: "5초는 유닛이 소리를 감지했을 때 그 인지반응이 유효한
시간이지, 소리 자체가 5초 동안 계속 발생 중이라는 뜻이 아니다."

기존 구현(PropagationSystem.EmitSound가 소리를 5초짜리 _activeSounds 리스트에 넣고, 모든 인류가
UnitFunction.OnUpdate의 0.1초 틱마다 TickSoundPerception으로 그 리스트 전체를 훑는 폴링 방식)은
정확히 반대로 동작하고 있었다 — 소리가 5초 동안 "월드에 남아있어서" 그 사이 범위 안으로 뒤늦게 걸어
들어온 유닛도 주워들을 수 있었다. 기획 관점에서도(소리는 순간적이어야 함), 최적화 관점에서도(모든
인류가 상시 폴링) 문제로 판단해 사용자가 직접 방향을 지시: "범위 스캔 후 R3 이벤트를 터뜨려 인지반응을
위한 5초를 UniTask 등으로 발동시키는 것."

[구현 방식]
PropagationSystem.cs 대폭 재작성:
- EmitSound가 호출된 그 자리에서 즉시 범위 스캔을 끝낸다(같은 층/같은 공간(roomId)/CanPerceive/
  IsSoundUnresponsive/이동음 자기·아군 제외/SoundDetectionRange 이내 — 예전 TickSoundPerception이
  각 인류 관점에서 하던 조건 판정을 소리 쪽에서 한 번에 수행).
- 조건을 만족하는 인류마다 PropagationSystem.OnSoundPerceived(R3 Subject<SoundPerceivedEvent>)로
  1회 통지 — 나중에 범위 안으로 들어온 유닛은 이 사건 자체를 아예 못 받는다(실제 소리처럼 순간적).
- HandleSoundPerceived(OnSoundPerceived 내부 구독자, static 생성자에서 자체 구독)가 실제
  PendingSound 갱신 담당. 우선순위/거리 비교 로직(7-2장)은 그대로 유지 — 여러 소리가 연속 발생해도
  R3 Subject.OnNext가 동기 호출이라 매번 "그 시점의 PendingSound"와 비교돼 결과적으로 가장 급한
  소리가 남는다(기존과 동일 결과 보장).
- ExpireAfterDelay(async UniTaskVoid) — UniTask.Delay(5초) 후 그 reaction이 여전히 PendingSound에
  남아있고 확인 행동을 아직 시작 안 했으면 null로 비운다. 감지된 시점 자체를 기준으로 한 명시적
  타이머라 다른 시스템의 틱 호출 유무에 기대지 않는다.
- UnitFunction.OnUpdate의 TickSoundPerception 반복 호출 삭제.

[검증]
dotnet build 확인. PropagationSystemTests.cs에 OnSoundPerceived 이벤트를 직접 발행해서 PendingSound
세팅/우선순위 유지·교체 규칙을 고정하는 테스트 추가. EmitSound 자체(범위 스캔)는 GameSession 풀
셋업이 필요해 단위 테스트 범위 밖 — 실제 플레이 검증 필요.

■ 3. 방별 인류 후보 인덱스 — EmitSound 스캔 최적화
════════════════════════════════════════════════════════════════════════
[배경]
위 2번 재설계 후 사용자가 "전체 순회 후 거리 계산 vs 후보를 먼저 좁히고 거리 계산, N=1/10/100/1000일
때 각각 O(N) 정리해달라"고 요청 → 답변: 전체 순회는 O(N²)(호출 수 O(N) × 순회당 O(N)), 방별 인덱스는
O(N·k)(k=같은 방 인원, 사실상 상수) — 인류 수가 아니라 "동시에 활동하는 방의 개수"가 늘어나는 시점이
최적화가 필요해지는 신호라고 설명. 사용자가 "방별 인덱스로 진행하자"고 결정.

[구현 방식]
PropagationSystem에 Dictionary<(int Floor, int RoomId), HashSet<Human>> _humansByRoom 추가(roomId는
층마다 번호가 재사용될 수 있어 (층, roomId) 튜플 키 사용). 유지보수는 새 폴링을 만들지 않고 기존
유닛 그리드 관리 지점(GameSession.RegisterUnitPos/UnregisterUnitPos — 스폰/이동/사망 시 이미 호출되는
곳)에 얹었다. WaveSpawner/HumanWaveManager/NavigationFSMState/DebugInputHandler 등 모든 인류
스폰·이동·제거 경로가 이 두 래퍼를 거치는 걸 확인해서 별도로 각 스폰 지점을 손댈 필요가 없었다.
EmitSound는 이제 session.units 전체 대신 _humansByRoom[(floorIndex, roomId)]만 순회 — 최종 거리
판정은 여전히 Vector2Int.Distance 좌표 수학 그대로(공간 분할은 후보를 줄이는 역할이지 거리 계산을
대체하지 않는다는 원칙 유지).

[검증]
dotnet build 확인. 인덱스 내부 상태를 직접 조회하는 public API가 없어 전용 단위 테스트는 없음 —
실제 플레이 검증 필요(방을 옮겨도 정상 작동하는지, 죽은 유닛이 인덱스에서 실제로 빠지는지).

■ 4. AlertSearchState 15초 워치독 오적용 버그 수정
════════════════════════════════════════════════════════════════════════
[배경]
사용자가 "소리 반응이 여러 번 겹칠 때 다른 로직과 꼬이는 부분이 있는지, 특히 전투 중 소리 들으면
어떻게 반응하는지 실제 반영 여부를 확인해달라"고 요청 → fork로 TacticalFSMState/CombatFSMState
우선순위 체계를 전수 조사(아래 7번). 우선순위 체계 자체는 설계대로 정확히 반영돼 있었지만, 실제
버그를 하나 발견했다.

[원인]
AlertSearchState.ElapsedSeconds 필드를 두 군데가 서로 다른 목적으로 공유해서 썼다.
- UnitFunction.OnUpdate: currentAlertSearch가 있으면 매 프레임 무조건 누적시키다가
  IsPostCombatSweep/IsDeathSearch가 아니면 03문서 4-11장 "미식별 공격 수색시간"(15초, "공격은
  당했는데 누가 때렸는지 모르는" 시나리오 전용)을 워치독으로 적용 — IsSoundResponse 여부를 전혀 안 봄.
- TacticalFSMState.SoundAreaApproach/SoundMoveReact: 인지 판정 롤 시점에 같은 필드를 0으로
  리셋해서 "롤 이후 2초 유지"용으로 재사용.

07-A 7-3장을 재확인한 결과 "확인 행동 시작 기한은 5초지만, 시작 후엔 시간 제한 없이 계속 수행"이라고
명시돼 있어 — 소리 반응 접근 자체엔 완료 시간 제한이 없는 게 문서 의도임을 확인. 15초는 소리 반응과
무관한 값인데, 감지 범위가 멀면(spotting 보정 포함 8~12칸까지 가능, 게다가 급하지 않은 소리는 경계
이동속도 75%까지 겹침) 도착 전에 이 워치독에 걸려 소리 반응이 조용히 통째로 취소되는 버그였다.
인지 판정 자체가 안 굴려지니 위 1번 E_HIT_HEAVY_INDIRECT 확인 기회도 함께 날아갔다.

[구현 방식]
UnitFunction.OnUpdate에 "IsSoundResponse && !SoundPerceptionRolled"(아직 접근 중) 조건이면 15초
워치독 자체를 적용하지 않는 예외 추가. 롤 이후엔 손댈 필요 없음 — 롤 시점에 ElapsedSeconds가 0으로
리셋되고 2초 규칙이 15초보다 항상 먼저 트리거되므로 워치독과 절대 안 겹친다.

[검증]
FSMBehaviorTests.cs에 신규 테스트 2개(소리 반응은 16초 지나도 안 잘리는지 / 원래 미식별 공격 수색은
여전히 15초에 잘리는지 — 회귀 방지). human.OnUpdate(deltaTime)을 직접 호출하는 이 프로젝트 최초의
테스트. dotnet build 확인.

■ 5. 유닛 겹침 버그 수정 — 계단 이동 텔레포트
════════════════════════════════════════════════════════════════════════
[배경]
사용자가 "유닛이 겹치는 것 같다. 유닛끼리 겹쳐서는 안 된다"고 신고. 언제 겹치는지 물었더니 "전부"
(평소 이동/전투/포메이션/스폰 다 겹쳐 보임)라고 답변 → fork로 스폰 배치/유닛 그리드 등록/CanMove를
우회하는 직접 위치 대입 지점을 전수 조사.

[원인]
계단으로 층을 넘는 "도착" 지점에서 겹치고 있었다(웨이브 기반 게임이라 파티가 몰려서 계단을 자주
오가므로 "전부 다 겹쳐 보인다"는 인상을 준 것으로 추정). 계단 "접근"(NavigationFSMState.MoveToStairs,
출발 층에서 계단으로 다가가는 것)은 이미 여러 후보 칸 중 점유 안 된 칸을 골라 이동하도록 돼 있었는데
(2026-07-23 병목 수정), "도착" 측 3곳은 그 수정이 안 된 채 남아 있었다:
- NavigationFSMState.CrossStairs — 힌트 없는 CreateMap.TryGetStairApproachPosition을 호출하는데,
  이 함수는 같은 (출발층,도착층) 조합이면 항상 정확히 같은 좌표 1칸만 반환한다. 점유 확인 없이 그
  자리로 바로 텔레포트.
- HumanWaveManager.ForceCrossToTargetFloor(강제 이동 타임아웃)/RetreatMemberToFloor0(웨이브 종료
  후 퇴각) — 둘 다 미리 캐시해둔 좌표 1칸으로 역시 점유 확인 없이 텔레포트. 특히 퇴각은 파티 전원을
  한 번에 순회하며 호출되는 코드라 여러 명이 동시에 정확히 같은 칸에 겹치는 게 사실상 확정적이었다.

[구현 방식]
AIMovementHelper.TryResolveUnoccupiedStairArrival 헬퍼 신설 — MoveToStairs가 이미 쓰던 방식(계단
주변 여러 후보 칸 + unitGrid 점유 확인)을 "도착" 측 3곳에 동일하게 적용.
- CrossStairs: 후보가 전부 점유돼 있으면(극단적 혼잡) 실패로 보고 다음 틱에 재시도 — 절대 겹치는
  칸으로 텔레포트하지 않음.
- ForceCrossToTargetFloor: 반환 타입을 void→bool로 바꿔서, 실패하면 이번 틱은 건너뛰고 staging에
  남아 다음 틱 재시도.
- RetreatMemberToFloor0: 일회성 호출이라 재시도 루프가 자연스럽지 않아, 후보가 전부 점유된 극단적
  경우에만 예전 방식(대표 좌표)으로 폴백하고 경고 로그를 남기게 함(완전히 막아 그 파티원이 영영
  못 돌아오게 하는 것보다 낫다는 판단).

[검증]
dotnet build 확인. 맵 생성이 필요해 자동화 테스트는 안 붙였음 — 플레이로 확인 필요(계단 넘나들 때
안 겹치는지, 강제 이동/퇴각 시 안 겹치는지).

■ 6. 임시 디버그 시각화(PropagationDebugVisualizer) — 신설 + 3차례 개선
════════════════════════════════════════════════════════════════════════
사용자가 "핵심 시스템(소리, 전파 범위)을 임시 시각화해달라"고 요청해서 신설, 이후 사용자 피드백으로
여러 차례 고쳤다. GameCompositionRoot/GameSession에 ThreatTileRenderer와 동일 컨벤션(GameObject
불필요한 순수 C# 클래스, 매 프레임 Render(units) 호출)으로 배선.

1차: LineRenderer + 즉석 Shader.Find("Sprites/Default") 머티리얼로 원 그림 → 실제로 켜봐도 안 보임
   (이 프로젝트가 URP라 검증 안 된 경로였음) → ThreatTileRenderer가 이미 증명한 방식(SpriteRenderer +
   절차적으로 생성한 원형 링 텍스처, 머티리얼은 SpriteRenderer 기본값에 맡김)으로 교체.
2차: 소리 플래시가 리스트 인덱스 위치로 풀에서 재사용되다가 프레임마다 다른 플래시로 재배정되는
   버그(사용자가 "한 프레임만에 사라지는 거 아니냐"고 지적) → 각 플래시가 발생 즉시 자기 전용
   GameObject를 만들어 만료까지 그대로 들고 있는 방식으로 교체.
3차: "감지 성공한 소리만 보인다"는 한계(사용자가 "몬스터 이동음이 안 보인다"고 신고, 실제로는
   IsSoundUnresponsive 등으로 걸러지면 원 자체가 안 뜨는 구조였음) → OnSoundPerceived(감지 성공 시만
   발동) 대신 OnSoundEmitted(감지 성공 여부와 무관하게 소리가 난 사건 자체) 신설해서 그쪽을 구독하도록
   변경 — 이제 감지 성공 여부와 무관하게 소리가 나면 무조건 범위 원이 뜬다.

UI: DebugInfoPanel에 "소리/전파 표시" 토글 추가 → 항목별(전파 범위 + 소리 6종) 개별 토글 7개로
분리 + 버튼 배경색을 켜짐/꺼짐에 따라 뚜렷하게 칠해 상태 가시성 개선 + StatusInfoPanel(자원 현황
등)과 겹쳐서 좌측 상단(UIManager의 죽은 코드 자리, 실질적으로 비어있던 공간)으로 재배치.

■ 7. FSM 우선순위 체계 전수 검증 (fork 조사, 코드 수정 없이 조사만)
════════════════════════════════════════════════════════════════════════
결과 — 설계대로 정확히 반영된 것:
- 전투 중(personalSpottedEnemies>0)이면 IsSoundUnresponsive가 스캔 후보에서 아예 제외 — 소리를
  못 받음. "전투 중 소리 들으면?"의 답은 "안 들림"이 의도대로 구현됨.
- 전체 우선순위: Panic → JoinCombatWait → 함정대응 → 소리반응(Alert) → 조사 → 대기 → 포메이션 →
  코어, Combat은 별도 상위 FSM이라 이 전부보다 항상 우선(CombatFSMState priority 100 vs
  TacticalFSMState priority 50).
- 함정 대응 중 소리 인터럽트(PropagationSystem.HasPendingInterruptingSound)가 실제로
  TrapResponse 분기 최상단 조건으로 걸려 있어 정상 동작.
- JoinCombatWait 우선순위(Panic 바로 다음) 확인됨.

부정확했던 문서 서술(동작엔 영향 없음): 근접/즉시타격 공격은 실제로 "피격 발생 공격음 → 공격
실행음" 순서로 남(전에 반대로 적었던 게 오류였음) — 우선순위 비교가 랭크 기반이라 결과는 동일.

남아있는 경미한 이슈(오늘은 수정 안 함): Combat 진입 시 소리반응 currentAlertSearch가 명시적으로
안 지워지고 방치됨 — 위 4번 수정으로 15초 안에는 결국 정리되므로 영구 스턱은 아니지만, 그 좁은
타이밍에 CombatFSMState.OnExit의 전투 후 스윕 세팅이 씹힐 가능성이 이론상 있음. 심각도 낮음, 다음
우선순위 후보로 남겨둠.
