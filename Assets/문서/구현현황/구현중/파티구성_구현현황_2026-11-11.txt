파티 구성 구현현황 (2026-11-11)

작성 목적: `Assets/문서/공식문서/파티구성/`(설계명세서 v0.4 = 구현 대상, 핵심본 v0.4 = 기획 의도 참고)의 구현 범위·구조·자리표시자·미구현을 기록한다. 이 시스템을 다시 손댈 때는 이 문서부터 확인한다(다른 구현현황 문서와 같은 관례 — 새로 구현/연결하면 이 문서를 직접 갱신, 대규모 갱신이면 새 날짜 파일 + 이전 파일 `지난거/` 이동).
사용자 확정(2026-11-11): ① 웨이브당 원정 파티 **1개 + 확장 가능한 구조**(`WavePlan.Parties` 리스트, 이번엔 1개만 스폰·추적) ② 문서가 후속 콘텐츠로 미룬 값은 **`Assets/Data/party_composition.json` 자리표시자**로 두고 이 문서에 표로 기록 ③ 독립 유닛·점령 파티는 기존처럼 별도 경로.

■ 이 문서가 채운 것 (이전엔 비어 있던 편성 층)
──────────────────────────────────────────────────────────────────
4~16장(집결·진형·보호·코어·후퇴·리더)은 이미 구현돼 있었다(`CLAUDE.md` 해당 절들). 비어 있던 건 "누가 어떤 컨셉·임무·규모로 들어오는가"였다 — `GameSession.CreateParty`가 임무·컨셉을 무작위로 찍었고, 임무 수량은 전역 상수(방 2·처치 5), 웨이브 구성은 `WaveData.parties` 수동 목록이었다.
· **임무(PartyType)와 컨셉(PartyConcept)을 분리**(2-4장): `PartyType`에 `CoreDestroy`·`Boss` 추가(끝에), `PartyConcept`에 `Vagrant`(부랑자) 추가.
· **편성 계획**(`PartyPlanner`): 진행 상황 → 임무 후보 → 가중치 추첨(사건이 지정하면 그 결과, `WaveData.forcedMission`) → 임무를 수행할 수 있는 컨셉·규모·슬롯. 입력은 웨이브 번호·던전 위험도·인류 거점 유무·코어 활성 이력·미완료 방 수·회수물/적 존재·거점 정원 부족분.
· **웨이브 연동**: 계획은 쿨다운 사이클마다 한 번(`HumanWaveManager.EnsureNextPlan`) 만들어 **게이지 아이콘·사전 스폰·즉시 스폰 폴백이 같은 구성**을 읽는다. 이전 웨이브 생존자는 **계획 인원의 부족분을 먼저 채우고** 모자란 만큼만 새로 스폰한다(예전엔 생존자가 얹혀 파티가 웨이브마다 불어났다). 웨이브 종료 때 계획을 비우고 다음 사이클에서 다시 만든다 — 생존자·웨이브 번호·위험도·거점·코어 활성이 다음 계획의 입력이 된다.
· **임무 수량**(`PartyMissionQuota`): 발급 시 고정, 요구된 수량 **전부** 처음 달성하는 순간만 집결 판단에 반영(5-1장).
· **독립 유닛**(부랑자): 리더 없는 `Party.IsIndependentGroup` — 웨이브 추적 컨테이너일 뿐 리더·집결·공동 이동·코어 조사를 만들지 않는다.

■ 장별 구현 현황 (✅구현 / 🔶부분·자리표시자 / ❌미구현)
──────────────────────────────────────────────────────────────────
1장 성립·구성   ✅ 컨셉/임무/단계/독립 유닛 용어 구분, 편성 데이터 항목(구성·콘텐츠 입력) = party_composition.json. 리더 선정·지휘 상실은 기존(리더 명령 문서).
2장 초기·후속   ✅ 부랑자(리더 없음·거점 없을 때만·MaxWave 3), 모험가 2~4·도적 4~6, 컨셉×단계 확장(JSON), 탱커·힐러·CC 필수 없음(슬롯 최소 수 0 허용). 🔶 군대·용병·용사는 `enabled:false`(콘텐츠 미정 — 초반 버프 값을 복사하지 않음, 2-3장).
3장 임무 선택   ✅ 후보 구성 → 가중치 → 컨셉, 사건 지정(`WaveData.useForcedMission/forcedMission`). 🔶 후보 가중치·minWave·해금 조건 전부 자리표시자. 🔶 "귀환 기록"은 지금 생존자·웨이브·위험도·거점·코어 활성으로 근사(기록 종류별 최소 수는 웨이브 콘텐츠 문서 대기).
3-2장 수량       ✅ 타일(1층 이상, 파티 전체 중복 금지)·방 B+E(발급 시 고정, 알려진 보스방은 B에서 제외, 새 방을 발견해도 요구 수 불변)·처치(웨이브 공통 집계, 목표만 파티별)·회수(오브젝트별 1회)·코어 파괴·점령. 🔶 B = 미완료 일반 방 수를 상한(1)으로 자른 값, E = 1 — 합이 옛 상수 2와 같다(자리표시자). ❌ 종류별 처치 반영 배율(`PartyGoalMath.MonsterKillWeight`는 균일 1.0). 🔶 "리더에게 완료 여부 제공" — 수량은 파티 단위 집계라 리더 한정 접근 제한은 두지 않았다(개인 지도는 합치지 않음).
4장 임무별 종료   ✅ 탐색·회수·소탕·점령은 기존. ✅ 코어 파괴(이 방에 공격 가능한 코어가 없을 때 — 조사→공격→파괴는 기존 코어 조사·공격), 보스(완료 표시 + 남은 교전 없음). 🔶 보스 임무는 `enabled:false`(개별 절차는 후속 콘텐츠, 4-3장).
5장 활동 흐름   ✅ 전체 임무 수량을 처음 달성한 순간만 집결 판단에 반영, 이후 증가는 새 집결을 만들지 않음(`Quota.HasPendingAchievement/ConsumeAchievement`). 집결 후 흩어지지 않기·새 방 개인 탐색·정상 귀환은 기존.
6~12장          ✅ 기존 구현(보고 이동·집결 기한 8초/+3초·수색 5초·진형·보호·코어 보고·조사) — 이번 변경 없음. 독립 유닛은 이 경로의 대상이 아니다(리더 없음).
13장 코어 처리   ✅ 13-2 독립 유닛은 코어를 기록만(`FindHostileRoomCore`가 독립 그룹을 제외 + `OnCoreDiscovered` 즉시 반환 — 리더 조사·공동 파괴·보고 이동 없음). 나머지는 기존.
14~16장         ✅ 기존 구현(전투 후 5초 경계·통로 확보·후퇴 20/15·점령 40/30·거점 회복 60/40·리더 상실 후 개인 후퇴 20%).
17장 점령·충원   ✅ 점령 임무의 수량 = 기초 시설 완공(`OnOccupied`), 점령 파티 입양 시 점령 수량으로 교체. 🔶 **17-3 충원**: 부족분 = 거점 정원 − 현장 생존 병력(`OccupationSystem.GarrisonShortfall`)을 계획의 `ReinforcementCount`와 로그로 남김. ❌ 후속 파티가 부족분만 데려와 점령 병력에 편입하는 실제 합류는 보류 — 거점 정원 수치가 아직 처음 출격 인원 자리표시자다(코어 점령 구현현황 14장 보류와 같은 이유).
18~19장 검증사례 ✅ P01(거점 없음 → 독립 유닛)은 `PartyCompositionTests`로 고정, 헤드리스 플레이로 부랑자 웨이브가 실제로 스폰·종료되는 것도 확인. 🔶 P29(독립 유닛이 코어를 발견해도 기록만)는 코드로만 보장(`FindHostileRoomCore`·`OnCoreDiscovered` 제외) — 플레이 미확인. 나머지 사례(P02~P28, P30)는 기존 시스템 몫이라 이번에 새로 검증하지 않았다.
20장 후속 콘텐츠 ❌ 컨셉별 위협 배율·진형 모양·활동 범위, 비활성/해제 함정 회수 여부, 여러 파티 경로 배정·합동 임무·코어 장치 운반 담당·특화 장비(20-4)는 문서가 후속으로 미뤘다.

■ 자리표시자·해석 (문서가 정하지 않아 제가 정한 것 — 틀리면 `party_composition.json`만 고치면 됨)
──────────────────────────────────────────────────────────────────
· 단계: 1단계(웨이브 1~3)·2단계(4~7)·3단계(8+). 던전 위험도 조건은 0 — 위험도 기준은 콘텐츠 문서 대기.
· 부랑자: 인류 거점이 하나도 없고 웨이브 ≤ 3일 때 100% 등장, 규모 2~3, 전사·도적·아처형·사제.
· 모험가 규모 2~4(단계 1)→3~4→4, 도적 4~6→5~6→6(2-2장 초기값 + 단계 확장은 자리표시자). 슬롯(유닛 종류·최소/최대·가중치)은 전부 임시.
· 임무 가중치: 탐색 4·회수 2(웨이브 2+, 회수물 존재)·소탕 3(적 존재)·코어 파괴 2(웨이브 3+, 코어 활성)·점령 2(웨이브 3+, 코어 활성). 점령은 기존 규칙(1층 코어 활성 뒤에만)을 `requiresActivatedCore`로 흡수했다.
· 수량: 탐색 타일 40·방 B+E(상한 1+1)·처치 5·회수 1.
· **계획 없이 만든 파티**(수동 WaveData·`WaveData.useCompositionPlanner=false`·디버그 점령 파티 스폰)는 옛 동작 — 임무·컨셉 무작위, 수량은 "방 2 또는 처치 5 중 하나"(`PartyMissionQuota.Legacy`).

■ 알려진 한계 / 미확인
──────────────────────────────────────────────────────────────────
· **초반 웨이브 동작이 바뀐다**: 인류 거점이 없는 웨이브 1~3은 부랑자(리더 없음)라 집결·코어 파괴를 하지 않는다 — 웨이브는 전멸·개인 후퇴(HP 20%)·전원 이탈로만 끝난다(승리 조건이 없다, 13-2장 그대로). 이를 끄려면 `party_composition.json`의 Vagrant `enabled:false` 또는 `chance`/`maxWave`를 줄인다.
· 계획은 맵·방이 만들어진 뒤에만 세운다(`EnsureNextPlan`이 방 수 0이면 다음 호출로 미룬다). 맵 로드 전 게이지 호출은 수동 목록으로 폴백한다.
· 다중 원정 파티 동시 등장은 데이터 구조만 준비(`WavePlan.Parties`) — 스폰·추적·입구 시퀀스·종료 판정은 아직 1개 파티 전제(`HumanWaveManager.activeParty`).
· 검증: `dotnet build` 오류 0·경고 71(기준선). Unity 배치 테스트 전체 1177 통과 / 30 실패(기준선과 같은 8개 픽스처 — CombatSimulation 3·CreateMapPlay 9·ExplorationSystem 1·FSMBehavior 4·PlayableClassSkill 7·PropagationSystem 1·RouteAssessment 1·WallAutoTile 4, 회귀 0). 신규 `PartyCompositionTests` 32건 통과.
· **헤드리스 플레이(2026-11-11, 에디터를 닫고 임시 드라이버 — 삭제함)**: ① 기본 json — 웨이브 1 계획 "부랑자 무리"(규모 2, 리더 없음) 생성 → 게이지 아이콘이 같은 구성 → 0층 사전 스폰 → 웨이브 시작 → 한 명 후퇴·한 명 사망으로 종료 → 웨이브 2 계획(규모 3)이 생존자 1명을 먼저 채우고 신규 2명만 스폰(합류 후 3명, 파티가 불어나지 않음), 예외 0. ② 부랑자를 일시로 끈 json — 웨이브 1 "도적 소탕 파티"(규모 6, 처치 0/5, 리더 선정·집결 판단·리더 사망 후 승계·처치 수량 증가 1.0/5 확인) → 웨이브 2 "모험가 소탕 파티"로 전환, 예외 0(json은 원복). 탐색 타일/방 수량·회수·코어 파괴·점령 임무의 실제 플레이 흐름과 17-3 충원은 아직 눈으로 확인하지 못했다.

■ 리팩토링 반영 (2026-11-11, 동작 불변)
──────────────────────────────────────────────────────────────────
· `HumanWaveManager.GetApproachingPartyTypeNames`는 게이지 UI(OnGUI)가 프레임마다 여러 번 부르므로, 원천(사전 스폰 파티·편성 계획·WaveData)과 인원 수·최대 개수가 같으면 같은 목록 인스턴스를 돌려준다(호출부는 읽기만 한다).
· 호환용 프로퍼티 `JustReachedRoomExploreQuota`를 제거하고 테스트를 `PartyMissionQuota` 직접 호출로 바꿨다. `PartyMissionQuota.CountTile`은 목표 수에서 멈춰 집합이 더 커지지 않는다.
· 신규·수정 파일의 주석을 압축했다.
· **검증 상태**: 리팩토링 뒤 `dotnet build` 오류 0·경고 71 확인. **Unity 배치 테스트는 리팩토링 뒤 재실행하지 못했다**(시스템 메모리 부족으로 중단) — 위의 1177/30은 리팩토링 전 수치이므로 메모리 여유가 생기면 다시 돌려 `PartyCompositionTests` 32건·`CoreReportTests`와 기준선(30 실패, 8개 픽스처)을 확인할 것.

──────────────────────────────────────────────────────────────────
· 방 탐색 B 상한(`roomBaseCap`)을 유지할지 제거할지 — 명세는 "임무 발급 시 미완료 방 B와 추가 방 E로 요구 수 B+E를 고정"이라 B의 상한을 적지 않았는데, 현재는 json 상한(`roomBaseCap`=1)으로 자른다.
· 회수 수량 집계에 시체 회수를 포함할지.
