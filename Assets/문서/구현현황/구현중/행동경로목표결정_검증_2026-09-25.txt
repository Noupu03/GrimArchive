## 00-01  파티 목표·개인 행동·이동 경로의 구분 — ✅통과

[검증할 내용] 임무 수행 중 전투나 점유 우회가 발생해도 파티 임무와 개인이 현재 수행하는 행동·경로를
구분하는가.

[근거]
- Party.Type은 GameSession.cs:890(CreateParty)에서 단 한 번만 대입되고, 전체 코드베이스에 다른
  재대입 지점 없음(grep 확인) — 전투가 끼어도 파티 임무가 안 바뀜은 구조적으로 보장.
- CombatFSMState.GetPriority(CombatFSMState.cs:10)가 personalSpottedEnemies에 살아있는 적이 있으면
  우선순위 반환, UnitFSM._states 배열에서 Combat(index 1)이 Tactical(index 2, Investigate 포함)보다
  앞섬 — 적 발견 시 개인 행동은 즉시 전투로 전환.
- TacticalFSMState.CanInvestigate(:221)는 피격/위협 인지 시 그 틱만 false를 반환하고
  ApplyInvestigateInterruptPenalty(:244)로 진행도 50%만 깎을 뿐 human.currentInvestigation 자체는
  안 지움. currentInvestigation = null 대입 지점은 코드 전체 4곳뿐(:581,603,643,658)이고 전부
  "대상 무효/수거완료" 케이스 — Combat이나 다른 시스템이 임의로 지우는 경로 없음. 혼잡 우회
  (FindNearbyOpenTile, :590)도 경유지만 바꿀 뿐 TargetObjectId는 그대로 — "우회 ≠ 목표 교체" 성립.
- MoveToInvestigateTarget/InvestigatePerform/PickUpObject 전부 매 틱 objectGrid에서 obj.IsCollected를

   [수정, 2026-09-26] 사용자 지시("이 부분은 공식 문서 내용을 따르자")에 따라 InPropagationRange/
   CanPropagate 중 임의로 고르지 않고, 05번 문서 4장이 인용하는 "일반 전파 조건"의 원 정의를 찾아
   확인했다 — 시야인지반응/GrimArchive_07_전파·소리·간접입력_개념_v0.2.docx.md 6장(92-100줄):
   "발신자와 수신자가 모두 비전투 상태 + 같은 공간 + 전파 범위 안 + 발신자가 실제 보유한 정보만 +
   수신자가 모르거나 더 최신"을 모두 만족해야 "일반 전파"다. 이 중 "모두 비전투"까지 포함하는 건
   `PropagationSystem.CanPropagate`(sender/receiver 둘 다 personalSpottedEnemies 확인 후
   InPropagationRange)뿐이고, `InPropagationRange` 단독은 코드 자체 주석(PropagationSystem.cs:293)이
   "6장 '비전투' 조건 제외 — 발견자가 이미 적을 인지한 예외(7-1장)·사망 정보 예외(8장)에서만
   재사용"이라고 스스로 범위를 한정한다. 집결 명령·해제는 그런 예외에 해당하지 않으므로 문서가
   가리키는 정확한 게이트는 **CanPropagate**로 확정.
   Party.TryStartRally(:195-200)·OnLeaderLearnsCore(:237-245) 양쪽의 파티원 순회에
   `if (m.currentRoom != Leader.currentRoom && !PropagationSystem.CanPropagate(Leader, m)) continue;`
   를 추가 — 같은 방(Leader 본인 포함)은 조건이 항상 거짓이라 그대로 통과(방 전체 전달 예외 유지),
   다른 방은 CanPropagate를 만족해야만 집결 명령을 받거나 집결 해제로 currentWait이 풀린다. 관련
   주석(:21-22, :162, :225-227) 갱신. 이 세션엔 Unity가 .sln/.csproj를 생성하지 않은 상태라 이번엔
   dotnet build로 확인하지 못했다 — 다음에 에디터를 열 때 컴파일 오류 여부 확인 필요(변경 자체는
   기존 foreach 안에 조건문 한 줄 추가+기존 정적 메서드 호출이라 문법적 위험은 낮다고 판단).

7. "이미 달성했다는 이유로 다음 방 진입 직후 다시 집결하지 않는다" → N/A(1~3번과 동일 사유 — 임무
   수량 달성이라는 사건 자체가 없어 검증 불가). 참고: MopUp/Recover가 "방금 들어온 새 방"에서도
   거의 즉시 활동종료 조건을 만족할 수 있다는 별도 관찰이 있었지만, 이는 01-06-2/01-06-3이 각각
   명시적으로 요구하는 설계(방 전체 탐색을 강제하지 않음)와 정확히 일치해 여기서는 지적하지 않는다.

8. "전체 임무 미달성이어도 현재 방의 탐색 종료 조건을 충족하면 해당 집결 절차를 적용한다" → ✅
   (트리비얼하게 성립) `IsRoomActivityComplete()`(Party.cs:39-57)는 애초에 "전체 임무 수량"이라는
   개념을 전혀 참조하지 않고 리더의 현재 방(`Leader.currentRoom`) 기준으로만 판단한다 — 전체 임무
   미달성 여부가 이 판정에 개입할 여지 자체가 없어 요구사항을 자동으로 만족한다.

[내용 요약] 임무 수량 집계 자체(1~3·7번)는 00-03/00-04에서 이미 세 번째로 확인된 스텁이라 새로
지적할 게 없다. 정보 격리(5번)와 방 단위 판단(4·8번)은 코드가 정확하다. 6번에서 "집결 명령·해제의
전달 범위"가 05번 문서 4장이 요구하는 이원 구조(같은 방=무조건, 다른 방=일반 전파 게이트)를 지키지
않고 모든 파티원에게 무조건 적용되는 실제 불일치를 새로 찾았다 — 필요한 게이트 함수가 이미 존재해
"시스템 부재"로 볼 수 없는, 지금 고칠 수 있는 범주의 버그로 판단한다.

[Claude 의견] 6번은 00-04에서 고친 PartyCoreReportSystem과 정확히 같은 성격(리더-파티원 간 정보
전달에 CanPropagate/InPropagationRange 게이트를 빠뜨린 것)이라 수정 자체는 간단해 보인다. 다만
이번에도 사용자 확인 없이 바로 고치지 않고 보고만 한다 — 고칠지, 게이트 함수로 InPropagationRange와
CanPropagate 중 무엇을 쓸지(수신자가 전투 중이어도 집결 명령 자체는 받아야 하는지 등 세부 판단이
필요해 보인다) 확인이 필요하다.

## 01-03  방 탐색 완료와 추가 방 수 — 🔶부분통과(B+E 요구 수량은 시스템 부재로 N/A — 00-03/00-04/
   01-02에 이어 네 번째 확인, 내부지형 확인·상태 분리 2개 하위항목은 실제 코드로 ✅ 확인)

[검증할 내용] 방 탐색 임무의 요구 수량이 최초 미완료 방 B개와 추가 방 E개의 합으로 유지되는가.
외곽뿐 아니라 내부 지형 전체의 시야 확인으로 방 탐색 완료를 판단하는가.

[근거 — 항목별]
1. "임무 발급 시 목표는 B+E로 고정, B만 완료해 종료 안 함, 새 방 발견마다 B 안 늘림" → N/A(스텁,
   네 번째 확인) 00-03(4번)·00-04(7번)·01-02(1~3·7번)에 이어 "임무 수량" 개념 자체가 코드에 없다는
   동일 결론의 네 번째 독립 확인 — 새로 찾을 게 없다.

2. "외곽 벽을 확인했어도 내부 미확인 지형이 남으면 방 탐색 완료가 아니다" → ✅
   완료 판정은 방 하나의 "전체 바닥 타일 수"(CreateMap.RuntimeAPI.cs:41-56 `GetRoomFloorTileCount`,
   벽 제외하고 타일 단위로 셈 — 주석:40 "청크 개수만으론 부정확해 타일 단위로 센다")를 ground-truth로
   받아, `PersonalMapKnowledge.ObserveRoomTileRevealed`(:499-510)가 유닛이 처음 본 벽 아닌 타일 하나당
   `RevealedFloorTiles`를 1씩 늘리고 `RevealedFloorTiles >= totalFloorTilesInRoom`일 때만
   `RoomExploreState.Complete`로 전환한다(:507-509, 비가역). 실제 반영 지점은 `UnitFunction.cs:614-621`
   과 `TerrainRevealHandler.cs:9-19`(둘 다 시야로 새 타일이 드러날 때 호출) — 외곽만 걸어서는 내부
   타일들의 `isFirstReveal`이 발생하지 않으므로 카운트가 채워지지 않아 Complete 전환이 안 된다.
   01-05(이미 검증됨)가 확인한 "모든 타일을 직접 밟을 필요는 없다"(시야로 충분)와도 모순 없음 — 벽에
   막혀 시야가 안 닿는 내부는 애초에 "본" 것 자체가 아니라서 반영되지 않을 뿐이다.

3. "이미 확인된 보스방은 일반 탐색 후보와 B에서 제외한다" / "새로 보스방으로 확인된 방은 완료
   조건 충족 시에만 수량 반영, 요구 방 수는 유지" → N/A(1번과 동일 사유 — B 자체가 없어 "B에서 제외"할
   대상이 없음). "보스방을 일반 탐색 후보에서 빼는가"라는 더 일반적인 질문은 01-10에서 전용으로
   검증할 예정이라 여기서 미리 확인하지 않는다.

4. "지형 확인과 인지·안전·상호작용 완료를 구분한다" → ✅
   `PersonalMapKnowledge.RoomKnowledge`(:462-472)가 지형 상태(`State`: Unexplored/Exploring/
   Complete)·개체별 인지 확인(`ConfirmedUnits`/`ConfirmedObjects` 딕셔너리, 위험도·흥미도 확정값)·
   수거 여부(`_knownCollectedObjects`, 00-07에서 확인)를 서로 다른 필드로 보관한다 — 방이
   `Complete`가 돼도 개별 몬스터·오브젝트를 실제로 인지 판정했는지는 별개(01-05에서 이미 확인된
   "판정 전 타일은 기본값 5/2 사용"과 정확히 맞물림).

[내용 요약] 이 항목의 핵심 요구사항(B+E 요구 수량 유지, 보스방 B 제외)은 임무 수량 시스템 자체가
없어 네 번째로 N/A 처리한다 — 이제 이 결론은 충분히 굳었다고 본다. 다만 이번엔 같은 '방 탐색'을

봐야 완료"·"지형 확인과 안전 확인은 별개"라는 문서의 취지 2가지는 코드로 정확히 확인할 수 있었다.
