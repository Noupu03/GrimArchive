■ Haare 프레임워크 규칙 준수 — MonoRoutine / NativeRoutine 판단 근거
════════════════════════════════════════════════════════════════════════
이번 구현은 새 MonoRoutine이나 NativeRoutine 클래스를 하나도 추가하지 않았다. 의도적인 선택이며
근거는 다음과 같다.

- 시야/인지 계산(VisionMath) 자체는 WeightMath와 동일하게 부수효과 없는 순수 정적 함수 모음이다.
  씬 GameObject도, Processor의 매 프레임 자동 호출도 필요 없다 — 그냥 값을 계산해 돌려주는 코드라
  Routine 자격 자체가 없다(Haare의 Routine은 "Processor에 자신을 등록해 생명주기 콜백을 받는" 것이
  핵심 계약인데, 정적 함수는 인스턴스가 없어 그 계약을 맺을 대상이 아니다).
- 시야/인지 판정(UpdateFOV/CastRay)과 시야 방향 갱신(ResolveVisionDirection)은 이미 존재하는
  GameSession(NativeRoutine).UpdateProcess() → ProcessUnitAction(u) 루프에 얹었다. GameSession이
  "인스펙터 데이터가 전혀 없는 순수 C# 클래스라 NativeRoutine으로 전환됐다"(GameCompositionRoot.cs
  주석)는 기존 판단을 그대로 재사용한 것 — 이 시스템만을 위해 별도의 Processor 등록 지점을 새로
  만들 이유가 없다.
- 공격 후 가시성 상승 타이머(attackVisibilityBoostTimer)도 새 Routine이 아니라 기존
  UnitFunction.OnUpdate(deltaTime)에 stunDuration/slowDuration 등과 같은 자리에 얹었다 — Unit
  자체가 ScriptableObject(VContainer가 UnitGenerate.GenerateUnitAtPos에서 수동 Inject)라 Haare의
  Routine 계층에 속하지 않는 기존 구조를 그대로 따른 것이다(가중치 시스템의 stunDuration 등과 동일
  전례, Unit.cs 참고).
- 결론: "MonoRoutine인지 NativeRoutine인지"의 올바른 답은 "둘 다 아니다"이다. 이 시스템은 씬에
  상주해야 할 시각 요소(예: FOV 콘 디버그 렌더러)도, 인스펙터로 편집할 데이터도, 별도의 Processor
  틱 등록도 필요하지 않는 순수 계산+기존 턴 루프 연동이기 때문이다. 만약 나중에 "시야/인지 범위를
  씬에 실시간으로 그려주는 디버그 시각화"가 필요해지면, 그건 ThreatTileRenderer(순수 C#, Update가
  아니라 GameSession이 매 프레임 명시적으로 Render()를 호출하는 방식)와 동일한 패턴 — 즉 그것도
  NativeRoutine이 아니라 "외부에서 호출해주는 순수 C# 렌더 메커니즘"이 될 가능성이 높다.

00장. 시야-인지-반응 상위구조 (구현 대상 아님 — 문서 패키지 지도)
════════════════════════════════════════════════════════════════════════
이 장 자체는 "01~10번 문서가 어떻게 연결되는가"를 정리한 지도라 구현 항목이 없다. 3장(적용 진영
구분 표)만 실제 코드 판단 기준으로 참고했다:
✅ 시야 범위/인지 범위는 인류·몬스터 공통 적용 — UpdateFOV/CastRay는 Human/Monster 구분 없이
   동일한 시야각(120도 고정)·시야/인지 거리 공식(spotting 기반)을 쓴다.
✅ 정신력에 따른 인지 확률 감소·대표 가중치 3종 판단은 인류 전용, 몬스터는 없음 — 이 부분은 이미
   가중치 시스템(HumanKnowledgeBase, Human.personalMap)이 인류 전용으로 구현해 뒀고 이번 작업이
   건드리지 않았다(그대로 유지).
❌ 은신/기습/위협 콜라이더 방어 반응이 "양측 공통"이라는 표 항목 중, 은신 스탯 자체(stealth
   필드)는 이번에 추가했지만 기습/위협 콜라이더 방어 반응은 06_전투반응·기습 문서가 아직 없어
   미구현(다른 문서 영역).

01장. 시야·인지범위·가시성 개념
════════════════════════════════════════════════════════════════════════
✅ 1절. 시야 시스템 2단 구조(시야 범위/인지 범위) — UpdateFOV가 매 턴 두 계층(viewDistance+
   viewAngle=120도 고정 / perceptionDistance+perceptionAngle)을 동시에 계산해 CastRay에 전달.
✅ 2절. 시야 범위에서 가능한 처리 1~5 — 타일 위치 확인(discoveredMap/RevealTile, 인지 범위 여부와
   무관하게 항상 실행)/비어있지 않은 타일 존재 판단(visionOnlyNonEmptyTiles)/임시 위험도·흥미도
   적용(VisionMath.TempWeightForVisionOnlyTile, 값만 계산 — 10장 목표재설정 문서 부재로 소비자
   없음)까지 구현. "경로 판단 정보 생성"은 10_목표설정 문서가 없어 미구현.
✅ 3절. 시야 범위 내 임시 위험도/흥미도(빈 타일 유지/비어있지 않은 타일 +5/인지 범위 진입 시 제거)
   — VisionMath.TempWeightForVisionOnlyTile() + CastRay의 inPerceptionRange 분기가 표 그대로 처리.
✅ 4절. 인지 범위(시야 범위 안쪽, 인지각 최대 도달 시 시야 범위 전체가 인지범위화) —
   VisionMath.AwarenessAngle()/IsAwarenessAngleMaxed(), UpdateFOV의 rayInPerceptionAngle 판정이
   centerAngle 기준 대칭 비교라 인지각=120도일 때 자연히 전체 커버(AwarenessAngle_MaxedOut 테스트).
🔶 5절. 안전 확인/안전 타일 — "인지 범위 안 + 완전 차단 안 됨 + 적 유닛 없음 + 위험 오브젝트 없음"
   조건 자체는 기존 PersonalMapKnowledge.TickTileSafety()가 이미 이 근사(threatPresent 체크)로
   구현해 뒀다(가중치 시스템 15장, 이번 작업 대상 아님 — 그대로 유지). "위험 오브젝트"의 정확한
   판정 기준(함정/방어건물 등)은 그런 엔티티가 없어 여전히 부분적.
✅ 6절. 오브젝트 범주(함정/건물/시체/전멸흔적) — 시체/전멸흔적은 InteractableObject.Tags로 이미
   구현(가중치 시스템, 이번 작업 대상 아님). 함정/건물 엔티티는 여전히 없음(06/전투 연산 문서 영역).
✅ 7절. 범위 판정 기준(타일 일부만 겹쳐도 판정 대상) — 기존 CastRay의 그리드 단위 레이마칭이
   이미 타일 단위로 겹침을 판정하므로 별도 구현 없이 자연히 성립.
✅ 8절. 감지 스탯의 영향(시야거리/인지거리/인지각/인지확률, 시야각은 고정) — VisionMath의
   ViewDistance/AwarenessDistance/AwarenessAngle이 전부 spotting 인자를 받는다. "인지 확률"만
   02-A 문서 부재로 실제 확률 산출은 없음(1번 우선순위 항목 참고).
✅ 9절. 대상 기본 가시성(벽 0/일반타일 100/유닛·오브젝트가 무효화) —
   VisionMath.ResolveBaseVisibility(), Unit.baseVisibility(기본 100)/InteractableObject.
   BaseVisibility(기본 100) 필드 신설.
✅ 10절. 은신(유닛 가시성을 낮춤) — Unit.stealth 필드 신설 + FinalVisibility()에서 단순 차감.
🔶 11절. 오브젝트/유닛 가림 보정, "이미 인지된 대상 유지" — 완전 차단(벽) 뒤 판정 불가는 기존
   CastRay의 벽 충돌 시 ray break로 이미 성립(추가 구현 불필요). 비벽 오브젝트/유닛에 의한 가림
   "보정값"의 정확한 산식은 05-A 문서 부재로 미구현. "이미 인지된 대상 유지" 지속성은 위 "다음
   우선순위 4번" 참고 — 구조적으로 미룸.
✅ 12절. 공격에 따른 가시성 상승(+10, 5초, 재공격 시 지속시간 초기화, 최대 100) —
   Unit.TriggerAttackVisibilityBoost()/attackVisibilityBoostTimer, SkillAction.BeginAttackCast의
   공격 실행 지점에서 자동 호출, UnitFunction.OnUpdate가 타이머 감소.
🔶 13절/14절. 시야 방향(이동/전투/스킬/경계/소리/기습/명령 등에 따른 갱신) — 스킬 사용/근접
   대상/공격 대상/이동 4종만 실제 후보로 연결(위 "다음 우선순위 3번" 참고). 나머지 사유는 대응
   시스템 부재로 후보를 만들 수 없어 자연히 제외.
✅ 15절. 특수 원형 인지 범위(엘리트/네메시스/보스, 일반 유닛엔 미적용) — Unit.isSpecialUnit 플래그
   재사용(전용 유닛 타입이 없어 가중치 시스템 7-1장이 이미 쓰던 플래그를 그대로 판정 기준으로
   채택 — 판단 근거를 여기 남긴다). UpdateFOV가 isSpecialUnit이면 360도 원형 스윕을 추가 실행.
✅ 16절. 인류/몬스터 차이(인지 이후 판단 방식) — 이미 가중치 시스템(인류)/GoapCore·Goals(몬스터
   역할군 AI)로 구현돼 있던 기존 구조 그대로(이번 작업이 건드리지 않음).

01-A장. 시야·인지범위·가시성 연산공식
════════════════════════════════════════════════════════════════════════
✅ 1장. 기본 변수 전체(감지 스탯 최대값/기본 시야각/기본 시야거리/기본 인지각/최대 인지각/기본
   인지거리/가시성 범위/공격후 가시성 상승량·지속시간/기습 기준/원형 인지 범위 대상) —
   VisionMath.cs 상단 상수 전부.
✅ 2장. 시야 거리 공식(기본 6칸+감지 20마다 +1칸, 시야각 120도 고정) — VisionMath.ViewDistance(),
   테스트로 전 구간 고정(ViewDistance_Table).
✅ 3장. 인지 거리 공식(기본 4칸+감지 20마다 +1칸) — VisionMath.AwarenessDistance(), 테스트 고정.
✅ 4장. 인지각 공식(기본 60도+감지 10마다 6도, 최대 120도) — VisionMath.AwarenessAngle(), 테스트
   고정(0/9/10/50/99/100 경계값 전부).
✅ 5장/6장. 시야/인지 범위 판정(원뿔, 부분 겹침 허용) — CastRay의 레이마칭 자체가 이미 타일 단위
   부분 겹침 판정(7절 근거와 동일).
✅ 7장. 시야 범위 내 임시 위험도/흥미도 공식(표 그대로: 빈타일 0/비어있지 않은 타일 +5/인지범위
   진입시 제거) — VisionMath.TempWeightForVisionOnlyTile() + CastRay 분기.
✅ 8장. 정확한 인지 조건(인지범위 안+완전차단 아님+인지성공판정) — 조건 1(인지범위 안)은
   inPerceptionRange, 조건 2(완전차단 아님)는 벽에서 ray break로 이미 보장. 조건 3(인지 성공
   판정)은 02-A 문서 부재로 확률 판정 자체가 없어 "인지 범위 진입=인지 성공"으로 근사(기존
   게임 동작과 동일선상의 근사 — 이번에 새로 도입한 근사가 아니라 기존 CastRay 구조를 이어받음).
✅ 9장. 공격에 따른 가시성 상승 처리(항목별 값 표) — VisionMath.AttackVisibilityBoostAmount(10)/
   AttackVisibilityBoostDuration(5), Unit.TriggerAttackVisibilityBoost/attackVisibilityBoostTimer,
   FinalVisibility()의 100 클램프로 "이미 최대치면 더 상승 안 함" 자동 성립. 테스트 고정
   (FinalVisibility_StealthAndAttackBoost).
🔶 10장. 비벽 오브젝트/유닛 가림 보정 — "세부 산식은 05-A에서 다룬다"고 문서가 직접 위임한 부분이라
   05-A 부재로 미구현(값 자체를 만들 근거가 없음).
✅ 11장. 시야 방향 전환 우선순위(1~10순위 표 + 동률 시 최근접 채택 + 플레이어 명령 항상 최우선) —
   VisionMath.PriorityRank()/DirStepDistance()/ResolveVisionDirection() 전부 구현, 11개 사유의
   랭크가 정확히 표와 일치(PriorityRank_Ordering 테스트). 실제 후보 구성은 4종만 연결(위 참고).
✅ 12장. 소리 방향에 따른 시야 방향 갱신 조건표 — 조건 판정 로직 자체(우선순위 랭크 SoundDetected=7)
   는 준비돼 있으나, 08_전파·소리 문서/시스템이 없어 후보를 실제로 만들 발생 지점이 없음(3번
   우선순위 항목과 동일 사유).
✅ 13장. 특수 원형 인지 범위(반지름 표 1/2/3칸, 엘리트·네메시스·보스 전용) —
   VisionMath.CircularPerceptionRadius(), 테스트 고정(CircularPerceptionRadius_Table). UpdateFOV의
   isSpecialUnit 분기가 실제로 360도 스윕을 실행(01장 15절과 동일 항목).
