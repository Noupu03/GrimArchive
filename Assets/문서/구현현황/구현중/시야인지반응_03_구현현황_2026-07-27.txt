■ 추가 세션(2026-07-27 같은 날 재개) — 문서 전체 재검증 + 미구현 요소 구현
════════════════════════════════════════════════════════════════════════
아래 본문(최초 작성분)은 그날 첫 세션 결과다. 같은 날 다시 이어서 문서 전체(2~15장)를 실제 코드와
장별로 대조하는 재검증을 했고, 그 결과 발견한 버그 수정 + 미구현 항목 구현까지 진행했다. 이 세션의
변경사항은 실제 플레이 검증 전이라 아래 본문의 장별 태그와 별개로 여기 요약한다.

**새로 발견한 버그(수정 완료)**
- 4-14/9-8: 함정으로 죽으면 사망 원인이 영원히 "미확인"으로 남는 버그. `TrapPass`가
  `unit.TakeDamage()`를 attacker 없이 호출해 `lastAttacker`가 전혀 안 채워졌었다. `Unit.
  lastTrapAttacker`(InteractableObject)를 신설해 TrapPass에서 채우고(동시에 lastAttacker는
  비움), `PartyDeathRecord.CauseTrap` + `PartyDeathSystem.TryConfirmTrapCause`로 "함정 원인
  확인"(위험도 이벤트는 없음, 4-14장이 몬스터 원인에만 이벤트를 요구) 경로를 추가했다. TrapPass의
  HP비율 안전장치 때문에 실제 발생 빈도는 낮을 것으로 추정되나 경로 자체는 없었음 — 이제 확인 시
  4-15 원인미상 수색이 불필요하게 발동하지 않는다.

**미구현이던 항목 신규 구현(전부 실제 플레이 미검증)**
- 4-2 경계 반응속도×1.2 — `UnitFunction.OnThreatDetected`의 reactionTimeMs 계산에
  `currentAlertSearch != null`일 때 `ExplorationMath.AlertReactionSpeedRatio` 곱하도록 연결.
  reactedAttackers 게이팅 덕분에 자연히 "최초 반응"에만 적용된다.
- 4-3 경계 이동속도×0.75 — `GameSession.ProcessUnitAction`의 actionCooldown 계산에
  `currentAlertSearch != null`이면 `ExplorationMath.AlertMoveSpeedRatio` 곱하도록 연결(walkSpeed
  기반 전체 행동 주기라 이동 외 행동에도 넓게 적용되지만, 경계 상태에서는 실질적으로 이동만
  하므로 문제 없음).
- 5-4/9-8 조사·함정 해제 중 반응속도 50% — 같은 reactionTimeMs 계산에 `ExplorationPenaltyActive`면
  추가로 InvestigatePenaltyRatio(0.5)를 곱함(시야/인지범위는 이미 적용돼 있었고 반응속도만 빠져
  있었음).
- 10장 대기/11장 집결 — 예전부터 존재하던 죽은 배선(`WaitState`/`Party.RallyPoint`/
  `IsRallyActive`/`ExecuteWait` BT리프, 전부 만들어져 있었지만 실제로 `currentWait`을 대입하는
  코드가 0건이었음)을 실제로 되살렸다. `Party.TryStartRally()`(전투/전투직후스윕 중인 파티원이
  하나도 없으면 리더 위치를 RallyPoint로 잡고 다른 파티원 전원에게 `currentWait`
  부여)을 `UnitFunction.OnUpdate`의 IsPostCombatSweep 종료 시점에서 호출하고, `Party.
  CheckRallyComplete()`(전원 도착 확인)를 `ExecuteWait`의 도착 판정 직후에 호출하도록 연결.
  리더 명령 전파 체계(08문서 부재)가 없어 "즉시 전 파티원이 리더 위치를 안다"로 근사(5-5/9-3장과
  동일 관례) — Party.cs에 이미 있던 주석이 정확히 이 설계를 미리 적어뒀었다.
- 6-6/6-7 보호 포메이션 시야방향 — `TacticalFSMState.HoldFormation`이 예전엔 그냥 상호작용
  대상을 바라보기만 했는데, `AssignFormationWatchDirection`으로 교체해 같은 대상을 호위 중인
  다른 파티원들과 위치(전방/후방 — dot product로 판정, 후방/전방 애매하면 "중간"으로 분류)
  기준으로 좌우 정렬 후 인원수별(1명/홀수/짝수) 정면·좌측전방·우측전방(후방 대칭) 방향을 배정한다.
  중간 구간은 좌/우 부호로, 애매한 중앙 잔여는 감시 인원이 가장 적은 방향으로 근사. 6-7장 벽 차단은
  `IsDirectionWallBlocked`가 그 방향으로 `VisionMath.ViewDistance` 칸만큼 `CreateMap.
  IsStaticTileWalkable`을 샘플링해 50% 이상 막히면 인접 방향(표대로 좌우전방/좌우후방 후보) →
  그마저 막히면 전체 8방향 중 막히지 않고 감시 인원 최소인 방향으로 재배정한다.

**다음 세션 최우선 확인 대상(전부 코드만 작성, 실제 플레이 0회)**
1. 10/11장: 실제로 전투 후 파티 전원이 10초 스윕을 마치면 집결이 발동하는지, 리더 위치로 다들
   모이고 정상적으로 IsRallyActive가 꺼지는지(멈춰서 안 풀리는 교착 없는지) 확인.
2. 6-6/6-7: 여러 호위가 실제로 서로 다른 방향을 보는지(정면 좌우 배치), 좁은 통로에서 벽 차단
   재배정이 실제로 발동하는지 확인.
3. 4-2/4-3/5-4/9-8 반응속도·이동속도 배율이 체감상 실제로 다르게 느껴지는지(수치 튜닝 필요할 수
   있음 — 밸런스 확정값 아님).
4. 4-14 함정 사망원인 버그 수정 — 실제로 함정으로 유닛을 죽여서(TrapPass 경로) 원인미상 수색이
   더 이상 트리거되지 않는지 확인(발생 자체가 드물어서 재현이 번거로울 수 있음).

   근사, "발견 유닛이 리더에게 이동해 직접 전파"라는 물리적 이동 단계는 구현 안 함) → 리더가

   도착 후 1초 합류 전파(CoreInteractionState.PropagationDone) → 조사 진행(내부 판단 8초,
   ExplorationMath.CoreInvestigateDurationSeconds) → 완료 시 파티 전체에 정보 등록. 리더가 전투 중이면
   전투가 자동으로 더 높은 FSM 우선순위라 마무리 후 코어로 감(전투 전 우선순위 로직 자동 충족).
   리더 승계는 CanContinueCore가 매 틱 "현재 리더"를 확인해 새 CoreInteractionState를 자연스럽게
   만들므로 별도 코드 없이 GameSession.CheckPartyWaveState의 기존 AssignLeaderIfNeeded 호출만으로
   충족된다. 8-1장(본인 피격/위협 시 중단)도 구현, 8-2장("보호 유닛 피격 시 유지" 예외)은
   AnyEscortHitThisTurn을 의도적으로 확인하지 않아 자동으로 충족. 후속 상호작용(코어 파괴, 인류
   메리트, 플레이어 디메리트)은 "코어·핵심방어목표" 문서가 아직 없어 스텁(조사 완료 기록까지만).
   테스트용 스폰 수단: InputManager C키(고스트 배치, O/P/M과 동일 관례) → GameSession.SpawnCoreAt.

   [2026-07-27 디버깅 경과 — 시행착오 3회 롤백 후 실제 원인 발견·수정]
   사용자가 최초 보고한 버그 2건("코어 조사 후에도 안 사라짐", "포메이션 유닛이 코어를 밟고 서있음")을
   고치려고 순서대로 (a) CoreInvestigatePerform 완료 시 Loot 분기 즉시 회수, (b) GetEscortSlotPosition
   겹침 회피, (c) CanInvestigate "리더면 코어에 양보" 조건까지 세 차례 시도했지만 전부 "코어를 그냥
   지나친다"는 증상이 재현돼 사용자 요청으로 전부 롤백했다(추측성 수정이 원인을 못 맞힌 것 — 이
   경험 자체가 아래 근본 원인과 무관했다는 뜻).
   추측을 멈추고 LogHelper 진단 로그(CorePartySystem.OnCoreDiscovered/TacticalFSMState.
   CanContinueCore/MoveToCore)를 추가해 실제 콘솔 로그를 확인한 결과 진짜 원인을 찾았다:
   **MoveToCore의 도착 판정(Chebyshev 거리)이 X/Y 좌표만 비교하고 층(Z)을 전혀 확인하지 않았다.**
   웨이브 시작 직후 리더가 아직 0층 사전 스폰 대기 구역에 있는 상태에서 코어(1층 보스방)가 발견되면,
   GetPriority가 층 상관없이 즉시 리더에게 코어 최우선순위를 줘버리고, MoveToCore는 리더의 현재 층
   좌표가 우연히 코어의 X/Y 근처면 "도착"으로 오판해 그 자리(코어가 실제로 없는 층)에서 조사 로직을
   그대로 실행했다 — 로그로 "리더가 코어 상호작용 시작"까지는 정상 발생하는데 그 이후 실제 이동은
   전혀 없었던 게 이 오작동 때문이었다(사용자가 "코어가 없는 이상한 곳에서 코어 로직이 실행되고
   있다"고 정확히 짚어낸 그대로).
   수정 3곳:
   - TacticalFSMState.GetPriority: 리더의 현재 층이 PendingCorePosition.z와 다르면 Tactical/코어
     우선순위를 아예 양보(0f)하고, 대신 human.pendingStairTargetFloor를 코어 층으로 세팅해 이미
     검증된 NavigationFSMState의 계단 이동 파이프라인(MoveToStairs/CrossStairs)이 실제로 층을
     넘겨주게 한다.
   - CanContinueCore: 방어적으로 층이 다르면 false(정상 경로면 위에서 이미 걸러짐).
   - MoveToCore: 방어적으로 층이 다르면 Chebyshev 비교 자체를 건너뛰고 Running만 반환(오도착 방지).
   사용자가 재테스트로 정상 동작(리더가 실제로 계단을 넘어 코어까지 도달)을 콘솔 로그로 확인했다 —
   진단용 [CoreDebug] 로그 3곳은 이후 전부 제거했다.
   층 버그 수정 확인 후, 원래 보고됐던 버그 2건(코어 미회수/포메이션 겹침)의 수정 (a)/(b)를 다시
   적용했다 — 이번엔 층 버그가 먼저 해결된 상태라 정상적으로 도달 자체가 되므로 두 수정 모두
   최종적으로 유효하다: CoreInvestigatePerform 완료 시 Loot 태그가 있으면(보스방 던전 코어) 즉시
   회수하고, GetEscortSlotPosition은 상호작용 오브젝트 위치와 겹치는 슬롯을 회피한다. (c)(CanInvestigate
   "리더면 코어에 양보")는 층 버그가 진짜 원인이었으므로 다시 넣지 않았다 — 굳이 필요하지도 않았다.
❌ 7-4. 파티 목표 포메이션 시야 방향(리더 배치 우선순위) — (무변경) 애초에 미구현이던 리더 배치

■ 검증 및 오류 수정 계획 (2026-07-27 세션 종료 시점 — 다음 세션 시작 시 여기부터 확인)

이번 세션은 7-3장 코어 시스템을 실제 플레이로 반복 검증하며 버그를 잡는 데 대부분의 시간을 썼다.
그 결과 코어 쪽은 상당히 검증됐지만, 같은 세션에서 구현한 다른 대형 시스템(4-12~15 사망, 9장 함정
개편, 7-2 파티목표 전파)은 코드만 작성됐고 실제 플레이 검증은 아직 못 했다. 다음 세션은 이 순서로
재개할 것을 권장한다.

**A. 실제 플레이로 검증 완료된 것**
- 7-3 코어: 발견 → (다른 층이면) 계단 이동 → 리더 도착 → 조사 → 회수까지 전체 흐름을 사용자가 직접
  재시작 테스트로 확인함(층 버그 수정 후). 콘솔 로그로도 파이프라인 각 단계를 직접 확인했다.

**B. 이번 세션에 마지막으로 고쳤지만 아직 재검증 안 된 것 (최우선 확인 대상)**
1. GetEscortSlotPosition "이동 중엔 후방 배치" 수정 — 보호 포메이션이 리더의 진행 경로를 막아 코어에
   영구히 도착 못 하던 문제의 근본 수정. 사용자에게 재테스트를 요청한 직후 세션이 종료돼 **결과
   확인 전**이다. 다음 세션에서 가장 먼저: 코어 발견 → 리더 이동 중 호위가 실제로 뒤에 붙는지 →
   도착 후 정상적으로 전방/좌우로 재배치되는지 확인.
2. MoveToCore의 "완전히 막히면 근처 빈 칸으로 우회" 방어책 — 위 1번이 근본 수정이라 이 방어책이
   실제로 발동하는 상황을 보기는 어려울 수 있으나, 여전히 안 풀리는 경우가 있는지 확인.
3. TacticalFSMState.MoveToCore의 StepOffObjectTile(코어 타일에 정확히 서면 한 칸 물러남)도 1번 수정
   이후로는 재확인 안 됨 — 리더가 여전히 코어 위에 정확히 서는 경우가 있는지 확인.

**C. 코드만 작성되고 실제 플레이 검증이 전혀 안 된 것 (우선순위 순)**

   진입 전 최고성공률 유닛 즉시확정, 미선정 유닛 인접1칸 회피, 선정 유닛 미도착시 수색(4-12~15
   사망처리 연동), 해제 성공시 도감 기록 — 이 전부가 한 번도 실제 함정으로 테스트된 적 없다. P키로
   함정을 배치하고 여러 인류가 있는 상태에서 발견시켜 전체 흐름을 확인할 것.

   (b) 나중에 시체를 발견한 유닛이 -5 받는지 (c) 원인이 확인되면 그 몬스터 위험도가 실제로 오르는지
   (DebugInfoPanel 등으로 확인) (d) 원인 미상이면 경계 수색이 실제로 발동하는지 확인 필요.

넓혔다. HumanWaveManager의 운반·탈출 로직과 리더의 발견~조사 절차는 서로 게이팅하지 않고 병행
동작한다(위 7-3장 판정 참고) — "다른 코어의 기능은 그대로 둔채"라는 요청을 지키기 위한 의도적
설계다.
