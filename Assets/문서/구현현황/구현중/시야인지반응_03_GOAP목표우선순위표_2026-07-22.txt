■ 0-1. 핵심 발견 — "고착 목표(Sticky Goal)" 구조가 GoapCore.cs에 필요하다
════════════════════════════════════════════════════════════════════════
03문서 2-1장 마지막 문장을 그대로 인용한다:

  "이미 수행 중인 조사나 함정 해제는 더 높은 우선순위의 후보가 새로 발생했다는 이유만으로 자동
   중단하지 않으며, 실제 중단 조건이 충족됐을 때만 중단한다."

그리고 10장(대기): "수상한 타일을 확인하더라도 대기 목적이 해결되지 않았다면 대기를 유지하며,
수상한 타일은 대기 종료 후 처리한다."

이 두 문장은 지금의 GoapBrain.JudgeState() 구조(매 프레임 모든 GetPriority()를 다시 비교해 그
순간 최고점을 즉시 선택)와 정면으로 충돌한다. 예를 들어 Goal_Investigate(94)가 진행 중인데 그
사이 근처에서 수상한 타일이 발생해 Goal_Alert(97)의 조건이 새로 참이 되면, 지금 구조는 97>94이므로
그 프레임에 즉시 Investigate를 버리고 Alert로 넘어간다 — 그런데 03문서는 "조사 중이었다면 5-6장의
명시적 중단 조건(공격받음/적 정확 인지/위협 콜라이더 인지/도주·후퇴 전환)이 충족되기 전까지는 계속
조사를 유지하라"고 요구한다. 순수 숫자 비교만으로는 이 요구를 만족할 수 없다.

■ 해결 방향 — GoapGoal에 ShouldInterrupt 가상 메서드 추가(제안)
```
public abstract class GoapGoal
{
    public string    Name;
    public GoapState DesiredState = new GoapState();
    public abstract float GetPriority(Unit unit);

    // 신규: 이 목표가 "현재 활성 목표"일 때, 더 높은 점수의 다른 목표가 있어도 무시하고 계속
    // 유지해야 하는가? 기본값 false = 기존 4개 목표(Panic/PlayerCommand/DefeatEnemy/Explore)는
    // 지금처럼 매 프레임 그냥 최고점을 다시 고른다(동작 변경 없음). 03문서가 명시적으로 "고착"을
    // 요구하는 목표(TrapResponse/Investigate/Wait)만 override해서 true를 반환하고, 각자의
    // 명시적 중단 조건을 별도로 검사한다.
    public virtual bool IsSticky(Unit unit) => false;

    // IsSticky가 true인 동안, 이 목표를 실제로 내려놓아야 하는 조건(각 하위 클래스가 문서의
    // "중단 조건" 목록을 그대로 옮겨 구현). 기본 구현은 GetPriority(unit) <= 0(스스로 조건 소멸)만
    // 확인 — TrapResponse/Investigate/Wait는 이걸 오버라이드해서 9-7/5-6/10장의 개별 조건을 추가한다.
    public virtual bool ShouldInterrupt(Unit unit) => GetPriority(unit) <= 0f;
}
```

GoapBrain.JudgeState() 수정(제안, 기존 로직 최소 변경):
```
GoapGoal bestGoal;
if (currentGoal != null && currentGoal.IsSticky(unit) && !currentGoal.ShouldInterrupt(unit))
{
    bestGoal = currentGoal; // 고착 유지 — 다른 목표의 점수를 아예 비교하지 않는다.
}
else
{
    // 기존 로직 그대로: 모든 GoapGoal.GetPriority()를 비교해 최고점 선택.
    bestGoal = /* 기존 foreach 최고점 탐색 */;
}
currentGoal = bestGoal;
```
`currentPlannedAction`처럼 `currentGoal` 참조를 GoapBrain에 필드로 하나 추가해야 한다(지금은 매
프레임 즉시 버려지고 다시 계산돼서 "이전 프레임에 뭘 하고 있었는지"를 기억하지 않음).

■ 왜 기존 4개 목표는 그대로 둬도 되는가
- Goal_Panic(150)/Goal_PlayerCommand(130/90) — 최상위권이라 애초에 더 높은 값에 밀릴 일이 거의 없고,
  03문서도 이 둘에 대해 고착을 요구하지 않는다.
- Goal_DefeatEnemy(100) — "적이 보이는 한 계속 100"이라는 조건 자체가 이미 사실상 고착과 동일한
  효과를 낸다(적이 안 보이면 자연히 0으로 떨어짐).
- Goal_Explore(10) — 최하위 폴백이라 고착 개념이 무의미.
따라서 이 구조 변경은 기존 동작을 하나도 바꾸지 않고(4개 목표는 `IsSticky` 기본값 false 그대로),
신규 3개 목표(TrapResponse/Investigate/Wait)에만 새 동작을 추가하는 형태다 — 다만 GoapBrain.
JudgeState()라는 공유 코어 파일을 건드리는 변경이라, 실제 구현 시작 시점에는 다른 작업자와 겹치는지
먼저 확인할 것(CLAUDE.md 관례).

■ Goal_Alert는 왜 고착이 아닌가
03문서에서 "자동 중단하지 않는다"는 문장은 2-1장이 "조사나 함정 해제"만 명시적으로 지목하고, 10장이
"대기"를 별도로 명시한다 — 경계(Alert)는 어느 쪽에도 포함되지 않는다. 4-12장이 정의하는 15초
수색시간도 GOAP 우선순위 재비교와는 별개로 Action_Alert 내부 타이머로 자연히 유지되므로(조건 자체가
15초간 계속 참으로 남아있는 것이지, 다른 목표에 안 밀리게 특별 보호가 필요한 게 아님), Goal_Alert는
`IsSticky`를 오버라이드하지 않고 기존처럼 매 프레임 재비교되는 게 맞다 — 예를 들어 경계 수색 중
새로운 함정을 발견하면(TrapResponse 140 > Alert 97) 그 프레임에 바로 함정 대응으로 넘어가도
문서를 어기지 않는다.

■ 3-1. Goal_TrapResponse — 140, 고착(IsSticky=true)
```
public override float GetPriority(Unit unit)
{
    if (!HasPerceivedUnhandledTrap(unit)) return 0f;
    if (unit.personalSpottedEnemies.Count > 0) return 0f; // 9-7장: 적 정확 인지 시 즉시 양보
    return 140f;
}

public override bool IsSticky(Unit unit) => true;

// 9-7장 "함정 해제 중단과 진행도" 목록을 전부 그대로 옮긴다 — 하나라도 참이면 고착을 풀고
// 전체 재평가로 넘어간다(그 결과 대개 DefeatEnemy나 Alert가 새로 선택됨).
public override bool ShouldInterrupt(Unit unit)
{
    if (GetPriority(unit) <= 0f) return true;               // 함정 사라짐/적 발견 등 자체 소멸
    if (unit.isHitThisTurn) return true;                     // "해제 유닛이 공격받음"
    if (HasPerceivedThreatCollider(unit)) return true;       // "위협 콜라이더를 인지함" — currentThreat 참고
    if (AnyFormationMemberHitThisTurn(unit)) return true;    // "보호 포메이션 유닛이 공격받음"
                                                               //   (파티 목표 개념 없음 → 예외 없이 항상 중단)
    if (IsTrapTriggered(unit) || IsTrapDestroyed(unit)) return true; // "함정이 작동함/파괴됨"
    if (IsFleeingOrRetreating(unit)) return true;             // "다른 문서 결과로 전투·도주·후퇴 전환"
    return false;
}
```
- `HasPerceivedThreatCollider`는 새 인지 판정을 도는 게 아니라, 인지 범위 안의 적 유닛 중
  `enemy.currentThreat != null`(공격 예고 중 — SkillAction.cs:51이 캐스팅 시작 시 이미 세팅하는
  기존 필드, AreaBasedDamageValidator/ThreatTileRenderer가 이미 같은 필드를 읽어 판정·시각화에
  쓰고 있음)인 대상이 있는지 직접 확인하는 raw 체크로 충분하다 — 텔레그래프는 "경고" 목적이라 정확
  인지 확률표를 또 거칠 필요가 없다는 게 이번 재검토의 판단(문서에 별도 판정 공식 명시 없음).
- `AnyFormationMemberHitThisTurn`은 이 유닛을 호위 중인 보호 유닛 목록(누가 들고 있을지는 아직
  미확정 — 5절 체크리스트 참고, 후보는 상호작용 유닛 자신이 리스트를 들거나 별도 레지스트리)을
  순회해 `isHitThisTurn`을 확인한다 — 8-2장의 "비목표 상호작용은 보호 유닛 피격 시 무조건 중단"
  규칙(파티 목표 개념이 없어 예외 분기 없이 항상 적용).
- `IsTrapTriggered`/`IsTrapDestroyed`/`IsFleeingOrRetreating`은 함정 엔티티·도주 시스템이 아직
  없어(CLAUDE.md 기존 갭) 지금은 항상 false를 반환하는 스텁으로 시작해도 무방 — 실제 엔티티가 생기면
  채운다.
- 근거: 2-1장(자율 반응 중 최우선), 9-7장(위 중단 조건 전체 목록).
- DesiredState 제안: `DesiredState["trapHandled"] = true`.

■ 8-0. 이 코드베이스의 GoapAction이 실제로 어떻게 동작하는지 — Effects는 "선언"일 뿐 "적용"이 아니다
GoapCore.cs를 다시 확인한 결과, GoapBrain.JudgeState()에는 goap.cpp(학습 자료)의 `applyEffect`에
해당하는 단계가 없다 — Effects는 오직 "이 Action이 지금 목표(bestGoal.DesiredState)와 관련 있는가"를
가려내는 필터로만 쓰이고, 실제 월드 스테이트에 기록되지 않는다. 즉:
  1. 매 틱 GoapBrain.JudgeState()가 모든 GoapGoal.GetPriority()를 다시 계산해 bestGoal을 고른다.
  2. bestGoal.DesiredState와 Effects가 겹치는 Action들 중 IsValid()==true고 Precondition을 만족하는
     "가장 비용이 낮은" 것 하나를 고른다.
  3. 그 Action.Execute()가 실제 게임 상태를 바꾼다(이동, 타이머 진행, 상호작용 등).
  4. 다음 틱에 다시 1번부터 — bestGoal의 GetPriority()가 여전히 0보다 크면(고착이면 ShouldInterrupt가
     false인 한) 같은 Action이 계속 재선택되며 Execute()가 누적 진행시킨다. 목표가 실제로 해결되는
     순간(예: 함정이 실제로 해제/우회/파괴/통과됨)은 GetPriority() 쪽 조건이 스스로 꺼지면서
     자연스럽게 종료된다 — Action이 "나 끝났다"고 Effects로 세계에 통보하는 절차는 없다.
기존 Action_EngageEnemy가 이미 정확히 이 패턴이다 — `Effects["enemyAlive"]=false`를 선언하지만
실제로 적이 죽었는지는 전혀 확인하지 않고, 매 틱 그냥 다시 선택돼 공격을 반복한다. 아래 설계도
전부 이 전제를 따른다 — "Effects=true"는 있는 시늉이 아니라 "이 Action이 이 목표와 관련 있다"는
매칭 키일 뿐이고, 실제 완료 판정은 Goal.GetPriority()가 담당한다.

이 코드베이스는 또한 두 가지 게이팅 스타일이 섞여 있다:
  - Action_PlayerCommandExecute/Action_RandomExplore: Preconditions 딕셔너리가 비어있고, IsValid()가
    실질적인 게이트.
  - Action_EngageEnemy: `AddPrecondition("enemyVisible", true)` 하나만 Preconditions 딕셔너리에 넣고
    IsValid()는 `=> true`(무조건 통과).
아래 신규 Action들은 전부 전자 스타일(IsValid()가 실질 게이트, Preconditions 딕셔너리는 비움)을
따른다 — 신규 목표들의 분기 조건이 대부분 "여러 값의 조합"이라 GoapState(문자열 키 bool 값 하나씩)
로 표현하기보다 IsValid() 안에서 직접 판단하는 쪽이 이 코드베이스의 지배적 관례와 더 맞는다고
판단했다(사용자 재확인 없이 결정 — Action_EngageEnemy처럼 Preconditions 딕셔너리를 쓰고 싶다면
언제든 나중에 바꿀 수 있는 지점).

**공유 원칙**: Goal.GetPriority()와 그 목표에 속한 Action들의 IsValid()는 절대 같은 판정 로직을
따로 구현하지 않는다 — 반드시 같은 private 헬퍼 메서드(예: `HasPerceivedUnhandledTrap(unit)`)를
공유 호출한다. GetPriority가 worldState 계산보다 먼저 실행되는 구조(JudgeState 참고)라 GoapState
딕셔너리 자체를 공유할 수는 없지만, 헬퍼 메서드 공유로 동일한 효과를 낸다.

■ 8-1. Goal_TrapResponse(DesiredState=["trapHandled"]=true) — Action 4종
9-4/9-8/9-9/9-10/9-11장의 "해제/우회/파괴/통과" 갈림길을 Cost 순서(낮을수록 우선 선택)로 그대로
옮긴다 — 여러 Action이 동시에 IsValid=true여도 GoapBrain이 자동으로 가장 낮은 Cost를 고르므로 별도
분기 로직이 필요 없다.

| Action | Cost | IsValid | Execute 요약 |
|---|---|---|---|
| Action_TrapDisarm | 1 | 함정 미기록 **또는** 기록+예상성공률>50% | 미기록: 정보 전파(파티원 전원 PersonalMapKnowledge에 등록, BroadcastWitnessEvent 패턴 재사용) 후 5초 합류 대기(내부 타이머) → 더 높은 성공률 유닛이 합류하면 그 유닛만 실제 해제 진행, 없으면 발견 유닛이 직접 진행. 기록: 즉시 위치 이동 후 해제 진행. 해제 성공 시 `Knowledge.RecordEvent(EventId.E_TRAP_DISARM_SELF/...)` 호출(함정_관련_요약.txt 확인 완료 — 이벤트 정의는 이미 있고 호출부만 없음) + PersonalMapKnowledge에 실제 성공률 기록(9-2장 오차범위 축소). |
| Action_TrapBypass | 2 | 위 조건 거짓 **AND** 대체 경로 존재 | 이동 경로를 우회 경로로 교체(MovementAlgorithm 재요청). |
| Action_TrapPass | 3 | 위 두 조건 거짓 **AND** (일반 통과 안전 기준 충족 **OR** 9-11장 아군보호 완화 기준 충족) | 함정 위치를 그대로 통과 이동, 통과 시 `E_TRAP_HIT_SELF`(맞았다면) 기록. |
| Action_TrapDestroy | 4 | 위 세 조건 전부 거짓 | 함정 Hp를 유닛 physicalAttack 기반으로 매 틱 감소(간이 구현 — 정식 Hitbox/SkillAction 경유 아님, 8-2절 한계 참고). Hp 0 도달 시 오브젝트 제거. |

Cost 1<2<3<4 순서가 정확히 9-4(해제 우선)→9-8(우회 차선)→9-9/9-10(파괴 또는 통과, 통과를
더 선호)의 문서 순서를 반영한다. Pass와 Destroy 조건이 겹칠 수 있는데(대체경로 없음+해제불가는
둘 다에 해당) Pass의 Cost가 더 낮아 안전 기준을 만족하면 항상 Pass가 이긴다 — 9-9/9-10장이 명시적
우선순위를 안 줘서 "더 빠르고 위험이 적은 쪽"을 기본값으로 삼은 판단이다.

■ 8-7. 이번에 발견한 한계(구현 시 참고, 이번 범위 밖)
- Action_TrapDestroy가 함정 Hp를 깎는 방식은 정식 Hitbox/SkillAction 경유가 아니라 매 틱 직접 감산
  하는 간이 구현이다 — InteractableObject를 타겟으로 하는 공격 판정 자체가 코드베이스에 없기
  때문(공격 시스템은 Unit만 타겟함). 나중에 InteractableObject도 공격 대상이 될 수 있는 정식
  체계가 생기면 교체 대상.
- "전투 중 이동 경로가 함정으로 막혀서 파괴"(9-9장 두 번째 용례)는 Goal_TrapResponse 자체가 적
  발견 시 0을 반환하도록 설계돼 있어(3-1절) 이 경로로는 트리거되지 않는다 — 이건 사실 Action_
  EngageEnemy(전투 중 이동)가 처리해야 할 별개의 케이스이고, 이번 8절 설계 범위 밖이다.
